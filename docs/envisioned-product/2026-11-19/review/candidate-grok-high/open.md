# 仍要取舍的点

已定的产品方向不在这里。下面两件不挡住对应单元的状态机或核对记录合入，但挡住真实发送和浏览器依赖。

## 邮件传输

U7 可以先合入。未配置传输时，确认之后的结果是未能发送，不会再用本地 uuid 显示已发送。

要做活体发送之前，需要选定一种传输。现有 Gmail 范围只有 `https://www.googleapis.com/auth/gmail.readonly`（`backend/app/services/calendar_secrets.py:41`）。

- 若选 Gmail 发送，范围要扩大，接受证据是发送调用返回的消息 id。
- 若选 SMTP，调用返回不等于远程消息 id。没有另行定义的接受证据之前，不能把 SMTP 成功显示成已发送。

两种都还没选定。响应丢失且对方没有给出任何编号时，没有查询办法。这一缺口不靠再选一次传输消失。没有编号就保持未知，不重发。

## 浏览器依赖

U10 只写核对，不加依赖。三个问题都要通过，操作者才可能另说一次「合」去加依赖。

1. 候选必须是执行者看得见的函数工具，写操作在发出前能被现有确认单拦住。
2. 未确认时，提交、付款、发送一次都不执行。
3. 结果要能放进步骤 payload，并带证据字段。只有截图不够。

Hermes `0e8e42164063bf426af328ef94e2001dcaf9db1f` 的 Browser Use 接法这次没有重读。实施时打开具体文件，打不开就保持未通过。Poke 与 Vesta 是案例，不是选定结论，也不是成功率。Playwright 不是这个后端。现有 errand-compose 不升级成它。

在此之前，没有连接器的下单请求停止在「没有可用的下单接口」，不打开网页去下单。
