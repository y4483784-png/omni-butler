# 待用户取舍与核对事项（open）

本清单只列 2026-11-19 定案之外、仍需操作者做实质取舍或通过验证关口决定的事项。已定案的产品方向（原地 Python/TypeScript 演进、SuperAgent 交互派活与后台执行分离、Flash 回答 + DeepSeek 独立 Search/Fetch、聊天原图直传 Flash、保留智谱嵌入/重排/入库识图、本轮禁网硬约束、无常驻停止按钮、服务端持久化与断线不取消、按进展看护、强制确认不抄自动允许、单设备独立登记哈希凭证）均不再重问。

## 1. 邮件真实发送提供方与凭据接法（对应 U6 / X1）

- **需取舍点**：真实发信接 Gmail API（在现有 Google OAuth 上新增 `https://www.googleapis.com/auth/gmail.send` 授权范围，单独引导重授权，不破坏现有 `gmail.readonly` 只读路径）还是接通用 SMTP（由用户或部署配置 SMTP 主机、端口、账号与加密口令）或两者并存按配置切换。
- **影响边界**：
  - 选 Gmail API 时，发送成功可获得服务端 `id`（Gmail message id），超时丢响应时可用发送前嵌入的 RFC 5322 `Message-ID` 或自定义头通过 `users.messages.list(q="rfc822msgid:...")` 对账，但依赖 Google OAuth 审核/测试用户名单与 `gmail.send` 授权。
  - 选 SMTP 时，不依赖 Google OAuth，但 SMTP 协议本身不保证返回远程消息 ID，也不提供标准「已发送文件夹」查询接口；若 250 响应在网络层丢失，系统只能保持 `unknown` 并提示人工核对，无法程序自动对账。
- **不阻塞范围**：不阻塞 U1–U5、U7–U9。U6 可先落地 `MailTransport` 抽象与确认单/对账状态机，待选定提供方后接具体适配器。

## 2. 浏览器后端候选验证与依赖选择关口（对应 U7 Part B / X3）

- **当前状态**：`Hermes + Browser Use` 仅为优先核对候选，尚未选定为依赖，未安装；现有 `services/errand-compose`（Playwright sync API）保持现网回退，不新增微服务也不静默引入依赖。Poke/Vesta 仅作产品分工与证据形态参考。
- **验证步骤（Spike，不改主干依赖，单独分支/沙箱验证）**：
  1. **Flash 适配核对**：读取 Browser Use 当前版本源码与 `deepseek-flash` OpenAI 兼容接口调用链，运行只读导航任务，验证 `deepseek-flash`（含/不含思考模式）能否稳定输出结构化浏览器动作且无 `400` 格式错误。
  2. **写操作前真阻断核对**：核对 Browser Use 的动作钩子/自定义工具拦截点，构造模拟结账页（登录、提交订单、点击支付按钮），验证在任何不可逆点击或表单提交前能否硬中断执行、交还参数给 Omni-Butler 签发 `ScheduleConfirmClaim`，未确认前零点击。
  3. **关联号与证据回传核对**：验证浏览器步骤结束后能否稳定返回结构化 JSON（商家 `order_id`、关联句柄、脱敏摘要、只读证据截图/PDF 路径）并经过 `_SEALED` 凭证脱敏过滤，不泄露密码/卡号/Cookie。
  4. **架构边界核对**：确认仅作为独立后台执行者的工具后端接入 `errand-compose` 容器，不引入 Hermes 网关或替代 SuperAgent 派活层。
- **选择关口（Go/No-Go 准入标准）**：
  - 上述 4 项验证全部通过并附实测日志，操作者明确批复后，才可将 Browser Use 纳入 `services/errand-compose` 依赖并开启接入单元；任一项不通过（尤其是写操作前无法硬阻断或与 Flash 不兼容），则继续保留连接器优先 + 现有受控 Playwright 驱动路线，另行评估候选。

## 3. 各任务角色的默认参数与用量呈现（对应 U1 / M3）

- **需取舍点**：
  1. 角色级可选参数（`chat`、`dispatch`/`router`、`worker`/`planner`、`judge` 各自的 `max_tokens`、`top_p`、`reasoning_effort`）是否全部保持「留空走 DeepSeek 服务端默认」，还是为个别角色指定具体上限。按 2026-11-19 定案，设计不编造具体数值。
  2. 真实记录的 `llm_usage_records` 用量（prompt/completion/cached/reasoning tokens 与 Search/Fetch 成功次数）是否只在管理员/审计接口可见，还是在前端聊天消息或设置页对普通用户展示，以及是否按官方价目估算费用。
- **不阻塞范围**：U1 先落地配置槽位（留空即省略字段走供应商默认）与真实用量持久化，不等待最终默认数值或前端展示决策。

## 4. 看门狗进展检查与无进展报告间隔（对应 U4 / T4）

- **需取舍点**：
  1. 无进展触发「先检查并向聊天发一次去重报告」的静默阈值（分钟数）。
  2. 首次报告后若持续无进展，提醒间隔以及是否需要最终人工一键取消之外的兜底动作（定案已确认不按创建满 20 分钟强停，也不因沉默直接判失败，仅明确失败或用户取消才结束；具体报告阈值未定，设计不编造秒数）。
- **不阻塞范围**：不阻塞 U1–U3、U5–U9。U4 将检查阈值配置化，单元测试与形式模型使用参数化常量验证不变量。

## 5. 桌面设备配对与初始令牌颁发交互方式（对应 U8 / X5）

- **需取舍点**：用户在安装包里登记新设备时，采用「登录网页设置页生成一次性配对码/令牌，手动粘贴到桌面安装包一次后本地安全存储」还是「桌面安装包登录同一账号后直接调用 `POST /api/desktop/devices` 现场登记并弹窗展示一次性设备令牌」。
- **不阻塞范围**：后端 `desktop_devices` 表结构、SHA-256 哈希认证、`hmac.compare_digest`、`PackageProof(device_id)` 与单设备撤销接口在两种交互下完全一致，不阻塞 U8 后端落地。

## 6. 历史项 R2 与 R3 的产品细则确认（低优先级，不阻塞主线）

- **R2（`event_inbox.py:239-248,430-458`）**：外部非邮件事件显式点名一个已 `completed` 的旧代际时，当前代码会通过 `open_alongside` 新开一个 `running` 任务。接入 U3 多任务 SuperAgent 后，是否保持「点名已完成代际则新开独立任务」还是改为「记为关联到新任务但先经派活层评估」，需操作者确认。
- **R3（`memory.py:587,657-664,881-886`）**：三处历史细节（`list_memories` 空 `user_id` 退回 `1`、省略 `generation` 的直接调用仍抽取、`settle_pending` 放弃时原地改原行而非追加账本行）是否顺手在 U3 或独立小维护 PR 中统一收口。

## 7. 智谱嵌入、重排与入库识图的未来替代（对应 M4，当前明确冻结）

- 2026-11-19 已定案当前只替换智谱网页搜索，保留智谱嵌入、重排与资料入库识图。本项仅作远期占位，待未来需要迁移时再评估候选模型、全量重建向量索引与回滚方案，当前不占排期。
