# 聊天日程四件事的修复计划

本文只定计划，不改代码。对应 PR 只含本文。依据是 `develop` @ `87cf941` 的实机：Google 日历已连接，账户时区 `Asia/Singapore`，当天 `2026-10-15`。

已经接上的日历不用再做一遍：不另设产品时区；「现在」只来自该账户的 IANA 时区；写入仍只走确认卡片；不做双向同步；列表、侧栏、冲突继续当场 `events.list`。下面四件事是连接之后仍然会错的。

不改这些：

- 卡片上的 `start_at` / `end_at` 继续是无偏移墙钟。确认时由 `GoogleCalendarProvider._insert_google_event`（`calendar_google.py` 771–776）另附账户 `timeZone`。给字符串加上 `+08:00` 会让 `ScheduleCard.toLocalInput`（`ScheduleCard.tsx` 17–21）按浏览器时区换算，墙钟数字会变。
- 不把只存在于 Google 的条目做成修改或撤销卡片。对上标题时仍回答「这条日程只在 Google 日历里，请在 Google 日历里改。」
- 冲突空隙仍是每个空隙只给一段所请求的时长（`free_gaps`，`calendar_local.py` 24–53）。第 4 节只改「有空吗」的回答，不改 409 的建议。
- 不缓存时区。用户在 Google 里改了时区，下一次仍读设置。
- 「明天三点」没有「下午」时仍是 03:00。`test_account_timezone_drives_now_window_and_open_search` 锁的是这个。本轮那句带了「下午」。

## 1. 创建抽槽用了模型编的日期

句子：「明天下午三点开个测试会议 Grok测试」。卡片开始时间 `2023-04-05T15:00:00`，标题「测试会议」，参与人 `["Grok测试"]`，起止都没有偏移。

### 原因

`execute_calendar` 已经把账户墙钟传进去了（`calendar_tool.py` 353–354 → `calendar_now`，`calendar.py` 564–573）。抽槽没有用它来覆盖模型。

`extract_event`（`calendar.py` 122–171）把句子交给 `complete_json`。系统提示（132–138）只要求无偏移的 ISO，没有「今天是哪一天」，也没有账户时区。模型填了 `2023-04-05T15:00:00` 之后，`_supplement_draft_from_message`（255–256）只在 `start_at is None` 时才调用 `_parse_time_from_message`。模型给了日期，正则就不再跑。

同一句用正则、并把 `now` 设为 `2026-10-15 10:00`，会得到 `2026-10-16 15:00`：`_CALENDAR_TIME` 匹配「明天下午三点」，前缀「明天下午」加 12 小时（`calendar.py` 275–294）。现有单测把 `complete_json` 打成空对象或一份正确 JSON，所以编造的日期测不到。

标题和参与人走的是模型，不是正则：

- 模型返回的标题「测试会议」非空，正则不覆盖（251–254）。`_infer_title`（264–272）只认「主题是…」，否则在「周会 / 月会 / 面试 / 晨会 / 例会 / 会议」里返回第一个出现的词。这句会得到「会议」，不会得到「测试会议」。
- 参与人「Grok测试」也来自模型。`_parse_participants`（232–241）只认「参与人 / 参会人 / 和」。这句没有这些词，正则得到空列表。非空的模型列表不会被清掉（260–261）。

结束时间：模型没给结束，`_finalize_prefill`（176–180）补开始后 1 小时。`_parse_dt`（191–196）去掉时区，`_iso`（`calendar_tool.py` 57–60）按 naive 输出，卡片里的 `timezone` 固定是 `""`（111）。无偏移是墙钟约定，要修的是日期。

### 改法

相对时间以 `calendar_now` 为准，不信模型的年月日。

- 句子能被相对解析器解析时，`start_at` 用解析结果。模型的 `start_at` 只在句子里写了同一个公历日期时保留（例如「2026-10-16」或「10月16日」）。`2023-04-05` 不在这句里，丢掉。
- 提示里可以写上这面墙钟，方便模型处理绝对日期。判定放在代码里。只改提示不够。
- 标题优先取「开个 / 安排 / 约个」后面的那一段。「开个测试会议」得到「测试会议」。不要再缩短成「会议」。关键词回退只在这段和模型标题都空时使用。
- 参与人只保留由「参与人 / 参会人 / 和 / 邀请」引进、并且出现在句子里的名字。否则丢掉。这句的「Grok测试」不进参与人，也不自动拼进标题。
- 用户没说结束时间时，结束仍是开始后 1 小时。
- 同一刀补上正则组合：`后天` 和 `下午` 是互斥前缀，「后天下午四点」会匹配到「下午四点」，变成今天 16:00。日词和上/下午要能连用。「明天下午」已经是一个前缀，本句不受影响。单独的「四点」仍是 04:00，不猜成下午。

### 测试

放在 `backend/tests/test_calendar_card.py`，`now` 固定为 `2026-10-15`：

- `complete_json` 返回 `2023-04-05T15:00:00`、标题「会议」、参与人 `["Grok测试"]`。句子用上面那句。草稿开始必须是 `2026-10-16 15:00`，结束 `16:00`，标题「测试会议」，参与人 `[]`。
- 已连接、时区 `Asia/Singapore` 时走 `execute_calendar`，卡片 `start_at` 以 `2026-10-16T15:00:00` 开头，且不含 `+` 或 `Z`。
- 「参与人 Grok测试」仍抽出该参与人。
- 「后天下午四点」相对 `2026-10-15` 是 `2026-10-17 16:00`。
- 现有「明天三点」→ 03:00 的断言保持不变。

## 2. 时区请求的网络错误被说成授权失效

### 原因

`CalendarTokenError` 的默认文案是「Google 日历授权已失效，请重新连接。」（`calendar_secrets.py` 65–66）。

时区读取在 `_fetch_timezone_value`（`calendar_google.py` 905–934）：

- 902 行是 `_access_token` 里没有连接行，这是真的未连接，保持 `CalendarTokenError`。
- 913 行先 `refresh_access_token`。刷新时的网络错误和任何非 200（`calendar_secrets.py` 226–233）也抛 `CalendarTokenError`。访问令牌到期时，代理错误到不了 923 行，用户看到的仍是重新连接。
- 921–923 行：时区 GET 的 `httpx.HTTPError` 抛 `CalendarTokenError`。
- 926–930 行：除 200 和 404 以外的状态码同样抛，包括 500/502。`test_missing_timezone_is_etc_gmt_not_process_zone`（`test_calendar_google.py` 1165–1168）把 500 锁成了 `CalendarTokenError`。
- 404、空值、非法 IANA 仍用 `Etc/GMT`（924–925、932–933、151–156）。这不变。

聊天里这个异常没有被日历工具接住。`calendar_now` 在 list、suggest、创建之前就调用（`calendar_tool.py` 208、223、353）。`gateway.invoke`（`gateway.py` 231–234）把它收成「工具治理拒绝「calendar」：执行异常：CalendarTokenError: …授权已失效…」。确认接口则把 `CalendarTokenError` 映射成 401（`api/calendar.py` 208–209、262–263、284–285）。

列表自己的 `try`（`calendar_google.py` 181–184）包住了 `timezone_name()`，所以列表失败会退回本地行。聊天在进列表之前就因为 `calendar_now` 失败了，走不到这层。

### 改法

网络失败和授权失败分开。

- 新增 `CalendarTransientError`，不要做成 `CalendarTokenError` 的子类。文案：「暂时连不上 Google 日历，请稍后再试。」
- 时区 GET：传输错误以及 502/503/504 先重试一次。仍失败则抛瞬时错误。401/403 仍是 `CalendarTokenError`。404 仍是 `Etc/GMT`。500 改为瞬时错误，并改掉上面那个断言。
- 同一次读取里的令牌刷新：传输错误和 5xx 同样是瞬时错误。400/401/403 仍是授权失效。授权码交换那条路径不动，它已经是 502。
- 聊天：`calendar_now` 的瞬时错误由工具返回上面那句，不出卡片，也不要变成「工具治理拒绝」。不要改用进程时区或浏览器时区来凑一个「现在」。
- 列表：把瞬时错误并进现有的读取失败分支，仍返回本地行和「暂时读不到 Google 日历…」。
- suggest：仍用「暂时读不到 Google 日历，不能建议空闲时段。」不出建议卡片。
- 确认：502，不写 Google，不插本地行。

### 测试

放在 `backend/tests/test_calendar_google.py`：

- 时区 GET 第一次 `httpx.HTTPError`、第二次 200：得到原时区，不抛 `CalendarTokenError`。
- 两次都失败，或状态 500：抛 `CalendarTransientError`，文案不含「重新连接」。状态接口仍是 `connected: true`，`timezone` 为 `""`。
- 状态 401：仍是 `CalendarTokenError`。404 仍是 `Etc/GMT`。
- 刷新接口网络失败：同样是瞬时错误，不改已存令牌。刷新 400：仍是 `CalendarTokenError`，令牌不改。
- `execute_calendar` 在时区 GET 失败时，`direct_answer` 是瞬时文案，`schedule_card` 为 `None`。
- 已连接的确认 POST 在时区 GET 失败时为 502，本地无新行。

## 3. 改期和撤销回答「没有找到对应日程」

### 原因

定位只查本地行。`find_event_candidates`（`calendar.py` 624–651）调用 `overlap_rows`。已连接时这个方法只查本地表（`calendar_google.py` 443–464），不读 `events.list`。

窗口在 `_lookup_window`（392–403）：

- 给了 `start_at`：只查那一天的 `[00:00, 次日 00:00)`。
- 只有标题：从 `calendar_now` 到 `2100-01-01`，已经结束的行进不来（`end_at > now`，`calendar_local.py` 95–98）。

撤销用 `draft.start_at`，改期用 `reference_start_at`（`calendar_tool.py` 375–379）。改期句子若拆不开，`apply_update_times` 会把 reference 清掉（607–610），于是改期退回按标题、从现在往将来找。撤销不会清掉模型填上的 `start_at`。模型若再编一个日期，窗口就是错误的那一天；侧栏用的是从今天起 7 天的 `events.list`，所以用户看得到、聊天对不上。

「取消明天下午的测试会议」里没有「点」，`_CALENDAR_TIME` 匹配不到。日期完全取决于模型。模型一旦给了 `start_at`，第 1 节那个补充逻辑不会改它。

标题是双向子串（`titles_match`，556–561）。参与人不参与查找。「Grok测试」对不上「测试会议」；「会议」对得上「测试会议」，也会对上别的会。改期时 `apply_update_times`（615–617）用 `_infer_title` 覆盖标题，含「会议」的从句会被收成「会议」。

本地没有、Google 上有、且标题在同一窗口对上时，回复应是「请在 Google 日历里改」（`_readonly_reply`，284–298）。对不上才是短句「没有找到对应日程。」（`_NOT_FOUND`，29、386）。读 Google 失败时句子更长，带「暂时读不到 Google 日历」。实机是短句，所以读取本身没有失败，是窗口或标题没对上。

若第 1 节那张 `2023-04-05` 的草稿被确认过，这条本地行已经结束。不带那个过去日期的撤销走「从现在往将来」，仍然找不到。这是那次错误写入的结果，不另做回填。

列表上的标题可能是当场盖上的 Google 摘要，库里的 `title` 不改（接入计划第 6.1 节）。查找仍用库里的标题，所以侧栏上改过的名字会找不到。

### 改法

第 1 节落地之后，句子里没写的日期不再进入 `start_at`。撤销没有可解析的日子时，按标题从现在搜到 2100，能找到还没结束的本地「测试会议」。

本刀只补查找本身：

- 用来比对的标题取句子里的「测试会议」，不用缩成「会议」的关键词，也不用没有标记的「Grok测试」。
- 已连接时，带 `external_id` 的本地行除了库内标题，也用这次 `events.list` 读到的摘要来比对。对上了就选这行本地 id。不把摘要写回数据库。
- 仍然没有本地行、只对上只读项时，保持「请在 Google 日历里改」，不出卡片。
- 不把查找扩成全量同步，也不为了找旧草稿去扫 2023 年。

### 测试

放在 `backend/tests/test_calendar_google.py`：

- 本地行标题「测试会议」、时间为 `2026-10-16 15:00`。`complete_json` 给 `start_at` `2023-04-05`、标题「Grok测试」。句子「取消测试会议」。结果是撤销卡片，`event_id` 是该行，行仍是 `active`。
- 同一句若只有 Google 只读项、标题「测试会议」：没有卡片，`direct_answer` 是「这条日程只在 Google 日历里，请在 Google 日历里改。」
- 本地行标题是旧的「周会」，`external_id` 对上的 Google 摘要是「测试会议」。句子「取消测试会议」选中该本地行，数据库里的 `title` 仍是「周会」。
- 两行都含「会议」时仍是选择卡片，而不是只剩关键词「会议」造成的误匹配。现有 `missed_title` 断言（约 2451–2455 行）保持短句「没有找到对应日程。」

## 4. 「明天下午四点有空吗」只建议 12:00–13:00

### 原因

「有空」走 suggest（`calendar_tool.py` 36、46–47），不解析「四点」。

`_suggest_window`（166–174）：有「明天」且有「下午」时，窗口是明天 `12:00` 到后天 `00:00`。`find_free_slots` 要 1 小时，最多 3 段（226–228）。

`free_gaps`（`calendar_local.py` 40–53）在每一段空隙的开头只放一段所请求的时长。明天全空时，12:00 到 24:00 是一段空隙，于是只返回 `12:00–13:00`。`limit=3` 填不满。

这不是工作时间裁出来的。设置里没有工作时间时，`find_free_slots` 使用整个窗口（`calendar_google.py` 420–439）。实机 API 不返回每周工作时间。同一行为被 `test_find_free_slots_unions_google_busy_without_working_hours` 附近的空窗断言锁住：空窗的第一段就是窗口起点起的一个 `duration`。

「明天下午四点有空吗」用第 1 节的解析器会得到明天 16:00。suggest 没有调用它。

### 改法

- 句子里有可解析的钟点：用账户墙钟算出那一小时（默认 1 小时）。空闲则直接说这个时间可以，建议卡片只放这一段。被占则在同一天的这段窗口里再给别的空隙。仍不写库。
- 没有钟点、而且整个窗口是一段空隙：回答这段时间都有空，不要只列开头的一小时。
- `free_gaps` 和创建冲突用的 `free_slots_for` 保持「每个空隙一段」。suggest 不再拿这个结果当作「四点有没有空」的答案。

### 测试

`now` 固定 `2026-10-15`，当天和明天都没有日程：

- 「明天下午四点有空吗」的 `direct_answer` 含 `2026-10-16 16:00`，不把 `12:00–13:00` 当成唯一建议。卡片 `mode=suggest`，`phase=info`，不写库。
- 明天 `16:00–17:00` 已有日程：回答里不把这一小时当作空闲，可以给出下午的另一段。
- 「明天下午有空吗」且全空：不把唯一建议写成 `12:00–13:00`。
- `test_find_free_slots_uses_gaps_without_working_hours` 的两段空隙断言不变。已有「不要出现工作时间四字」的 suggest 断言保留；若空窗文案不再是「可以考虑这些空闲时段」，只改那一条文案断言。
