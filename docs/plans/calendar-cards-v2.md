# 日历卡片

本文只定计划，不改产品代码。对应 PR 只含本文。

四件事：空档询问先列出当天日程，再让模型挑时段；日程列表改成只读列表卡；会议和时间块分成两张创建卡；两张创建卡都可以带备注。守住已有边界：「现在」只来自账户 IANA 时区；写入必须先出确认卡；不做双向同步；列表当场 `events.list`，读完不落库；只做桌面 OAuth；`start_at` / `end_at` 保持无偏移墙钟；相信模型，不加正则兜底。不新做工作时间。

## 1. 空档询问

「明天有空吗」仍因「有空」进 suggest。不新加正则，也不再用 `_suggest_window`、`_named_clock` 或 `find_free_slots` 生成推荐。

现在没写「下午」时，窗口从当天 00:00 起。`find_free_slots` 在空隙开头放一段 1 小时，整天都空时第一段就是 `00:00–01:00`。这不是工作时间裁出来的。这里不加工时设置，也不在代码里按钟点删掉夜间。

哪一天交给模型，和 list 的 `day` 一样。点名了某一天就列那一天，墙钟 00:00 到次日 00:00。`day` 为空就用从账户「现在」当天 0 点起的 7 天。代码不解析「明天」「下午」「四点」。

先 `provider.list_events`。已连接是 primary `events.list`，读完不落库；未连接只有本地行。再调用一次模型，传入今天、时区 id、刚列出的标题和墙钟，以及用户原句。模型返回少量时段和一句说明。提示写明：按列出的这一天挑合适时段；不要推荐半夜到清晨，除非用户明确要夜里，或这一天只剩夜里有空；不要编造日程，不要创建。代码不改模型给出的钟点。模型若仍返回 `00:00`，照样显示。

时段放在同一张列表卡的 `suggested_slots` 上，渲染成现有的「用这个时段」。点了只在前端换成一张创建草稿，不写库。说明句放在卡片下面的文字里。这句不是密度建议，不调用 list 那次建议模型。

读失败时不调用挑时段的模型，不出列表卡，沿用「暂时读不到 Google 日历，不能建议空闲时段。」不把没读到的时间说成空闲。模型调用失败时，有事件则列表卡照常，文字接「暂时给不出建议」，`suggested_slots` 为空，不退回 `find_free_slots`。

用户接着说「就订明天下午三点」是新的一句，走第 3 节的确认卡。冲突回复用的 `free_slots_for` 不动。

## 2. 只读列表卡

查日程、怎么安排、以及空档回复里的事件，都用同一张只读列表卡。一行一条：时间加标题。全天写日期和「全天」。不写参与人，不写「来自 Google」。没有确认按钮。

`mode=list`，`phase=info`。它不是草稿，下一句不会被标成未确认。没有事件时不发空卡，文字仍是「这一天没有日程。」或「接下来 7 天没有日程。」

list 的建议仍由现在这次 `complete_text` 来写，只评论密度、缓冲、整段空闲和是否过载。建议留在卡片下面，作为普通文字，不再把日程行抄进 `direct_answer`。气泡里这种卡排在文字上面。创建、改期、撤销仍是说明在上、卡片在下。

读失败或没列完时不调用建议模型。通知下若还有本地行，列表卡只用这些行，文字是现有那句，不追加建议。建议模型自己失败时，列表卡照常，文字接「暂时给不出建议」。

空档回复有事件时用这张卡；推荐时段是第 1 节的按钮和下面那句说明。没有事件时不发空列表，只保留模型返回的时段按钮和那句说明。新回复不再发 `mode=suggest`。已经存下的旧 suggest 卡照旧能渲染。

## 3. 会议卡和时间块卡

创建抽槽让模型给出 `kind`：`meeting` 或 `block`。开会或有别人参加是 meeting；留给自己的一段时间是 block；拿不准就 meeting。缺省、空或其他值都当 meeting。不用正则把「写报告」改成 block。说了时长仍由模型写 `end_at`。

会议卡保持现有字段：标题、开始、结束、参与人（可空）、地点，加上第 4 节的备注。时间块卡只有标题、开始、时长和备注，不显示参与人，也不显示地点。时长由开始和结束推出来给用户改；改时长只改 `end_at`。线上和库里仍是无偏移的 `start_at` / `end_at`，不加时长列，也不加新的 API 字段。

两张都是 `phase=draft`。点确认之前不写 Google，不插本地行。冲突、过期、下一句作废，都沿用创建。时间块确认时参与人传空数组。Google 仍是普通事件，参与人仍不作为 attendees 发出。

## 4. 备注

两张创建卡都有可空的备注，就是现有的 `description`。界面可以仍叫「说明」，不另加一列。抽槽多收这个可空字段；用户没说就空字符串，不放进 `missing_fields`。

确认时走已经有的写入：Google 事件的 description，以及本地行的 description。空备注也允许确认。

## 5. 改期、撤销和 SSE

一条回复仍是一个 SSE 事件：`{"type":"schedule_card","card":{...}}`。先发这张卡，再发文字 token。不改成数组，不加第二种事件名。卡存在 `messages.schedule_card`。

卡上新增两个字段：

- `kind`：`meeting`、`block` 或 `""`。旧消息没有它时，前端按 meeting 渲染。
- `items`：`[{title, start_at, end_at, all_day}]`。只有 `mode=list` 才有内容，其他模式是空数组。

各模式：

- list：`mode=list`，`phase=info`，`items` 为行。空档回复才填 `suggested_slots`，查日程和怎么安排留空。`direct_answer` 是卡片下面的文字。
- create：`mode=create`，`phase=draft`，`kind` 为 meeting 或 block，`description` 为备注。
- update：仍是 `mode=update`，`phase=draft`，确认前不写。`kind` 只决定表单。meeting 保留参与人；block 显示标题、开始、时长、备注，不显示参与人。确认后仍走现有 patch。对不上标题则这次确认失败，不写。时间块改期确认时参与人传空数组。抽槽不强制填备注；说明框保持可手填。
- cancel：仍是 `mode=cancel`，`phase=draft`。不按 `kind` 换表单，不编辑时长，不编辑备注。标题可改，时间锁定，确认后才 delete。
- choose：未连接且多条本地匹配，保持现状。

改期和撤销不带 `items`，不会变成列表卡。列表卡和确认卡不会出现在同一条回复里。

## 6. 切片

四刀，都进 `develop`。模型返回值由测试给定。`now` 固定 `2026-10-15`，已连接时区 `Asia/Singapore`。

### 1. 只读列表卡

list 有事件就发 `mode=list`。`direct_answer` 只剩建议。

测试在 `backend/tests/test_calendar_card.py`：

- 模型给出 `day=2026-10-16`，当天有「周会」：`list_events` 的窗口是这一天的 00:00 到次日 00:00。`items` 含「周会」和它的墙钟，起止不含 `+` 或 `Z`。`mode=list`，`phase=info`，`suggested_slots` 为空。`direct_answer` 等于建议模型的返回。建议提示含列表、`2026-10-15` 和 `Asia/Singapore`，并写明不要逐段填空。`calendar_events` 条数不变。
- `day` 为空：窗口是 `2026-10-15` 0 点起的 7 天。有行则同样是列表卡。
- 没有行：`schedule_card` 为 `None`。文字含「这一天没有日程。」或 7 天那句，再接建议。
- `events.list` 失败：不调用建议模型。有本地行则列表卡只用这些行，文字含「暂时读不到 Google 日历」。
- 建议模型抛错：列表卡仍在，文字含「暂时给不出建议」。

前端 `frontend/tests/scheduleCard.test.mjs`：`mode=list` 只有时间和标题，没有确认按钮。`ChatWindow` 在这种卡上先渲染卡片，再渲染文字。

实机（桌面，已连接）：

1. 明天已有一场会。说「明天有什么安排」，再说「帮我看看明天怎么安排」。两句都先是一行时间加标题，下面是建议。没有确认按钮，Google 没有新日程。
2. 点名没有日程的一天：没有列表卡，只有「没有日程」和建议。
3. 断开或让读取失败：只看到暂时读不到。没有编出来的空闲，也没有建议段。

### 2. 空档先列表，再让模型挑时段

改 suggest。不调用 `find_free_slots`。

测试在 `backend/tests/test_calendar_card.py`：

- 「明天有空吗」，模型给出 `day=2026-10-16`，当天有「周会」：窗口是这一天。`items` 含「周会」。挑时段的提示含「周会」、`2026-10-15`、`Asia/Singapore`，并写明不要推荐半夜。模型返回 `15:00–16:00` 时，`suggested_slots` 就是这段，不是 `00:00–01:00`。`mode=list`，`phase=info`。下面的文字是模型的说明，不是密度建议。不写库。
- 当天没有日程：没有列表行。回答里的时段来自模型，不是算法造出的 `00:00–01:00`。
- 模型返回 `00:00–01:00`：卡片照样带上这段。测试不要求代码把它删掉。
- `events.list` 失败：文字是「暂时读不到 Google 日历，不能建议空闲时段。」`schedule_card` 为 `None`，不调用挑时段的模型。
- 挑时段的模型抛错：有事件则列表卡还在，文字含「暂时给不出建议」，`suggested_slots` 为空。
- 现有冲突空隙测试不改。

实机：

1. 明天上午已有一场会。说「明天有空吗」。先看到这场会，下面有推荐时段。推荐不是 `00:00–01:00`。没有确认按钮，Google 不变。点「用这个时段」只换成一张创建草稿，确认前仍不写入。
2. 明天全空。同样不是从午夜起的第一小时。文案不写「已按工作时间过滤」。
3. 接着说「就订明天下午三点的会」：一张会议确认卡。确认前 Google 不变。

### 3. 会议卡和时间块卡

改创建抽槽和创建卡表单。改期卡按 `kind` 换表单。撤销卡不动。

测试在 `backend/tests/test_calendar_card.py`：

- 创建提示含今天、`Asia/Singapore`，以及 meeting / block 的那句说明。
- 模型返回 `kind=block`、标题「写报告」、`2026-10-16T15:00:00`、`2026-10-16T17:00:00`、参与人 `[]`：卡片就是这些值，`kind=block`，`mode=create`，`phase=draft`。起止不含 `+` 或 `Z`。不写库。
- 模型返回 `kind=meeting` 且有参与人：卡片保留参与人。
- `kind` 为空：按 meeting。
- 模型没给 `end_at`：结束仍是开始后 1 小时。
- 改期抽槽 `kind=block`：确认卡的 `kind=block`，确认前无 patch。`kind` 缺省的改期卡仍按 meeting。
- 撤销仍是 `mode=cancel`，不因 `kind` 变成时间块表单。

前端：block 不渲染参与人，渲染由起止推出的时长；meeting 仍有参与人。两种都有确认按钮。

实机：

1. 「明天下午留两小时写报告」：时间块卡，有标题、时间和时长，没有参与人。确认前 Google 没有。确认后有一条，墙钟与卡片一致。
2. 「明早十点开周会，参与人小李」：会议卡，有参与人。确认前不写入。
3. 「把写报告改到后天下午」：改期确认卡，没有参与人栏。确认前 Google 不变。
4. 「取消周会」：仍是撤销确认卡。确认前不删除。

### 4. 备注写入 description

测试在 `backend/tests/test_calendar_card.py`，已连接的写入断言放在 `backend/tests/test_calendar_google.py`：

- 模型返回备注「带上大纲」：会议卡和时间块卡的 `description` 都是这句。缺备注不进 `missing_fields`。
- 确认请求体里的 description 相同。已连接时 Google insert 的 `description` 是这句，本地行也是。起止仍无偏移。
- 备注为空：仍可确认，Google `description` 为 `""`。
- 撤销确认不提交对 description 的修改。

实机：两张创建卡都能填备注。确认后在 Google 事件说明里看得到。留空也能确认。
