# 评测系统白话说明

这份说明只讲三件事：测的是什么、代码怎么走、你怎么跑。

对照的是正式线 `release` 上的旧评测，和当前实验线 `wip/eval-snapshot-1010`（提交 `406832a`）。正式线没有被这条实验线改掉。文里不写实测分数。代码里的及格线会标明是「门槛」，不是「这次跑出来的成绩」。

先记住三句：

- 离线测试不花钱、不连大模型，用来看代码和题目有没有写坏。
- 单环节测试分别打路由、检索、表格、上下文、依据核验，而且要打到线上真正用的那一段代码。
- 整段办事只有一套适合拿去对外讲。命令里叫 `agent`。旧的旁路套件 `yz` 已经从登记册拿掉，不要再引用它的分数。

读的时候，一个技术名字第一次出现会先用白话说清在干什么。后面的括号或句末只是方便你在仓库里找到它，不靠它也能读懂这一段。

---

## 1. 改之前出了什么问题，改之后变成什么样

旧评测的毛病可以收成三类。

**走错了路。** 很多分数测的不是用户真正会碰到的代码。路由直接问旧的分类器，绕过了线上那步「先决定调哪些工具」。检索一直关掉「关键词加向量一起搜」，也没有按正式入库的方式切块。表格测的是一套手写规则，不是线上那个让模型来规划的步骤。整段问答绕开了真正的办事流程。

**分数不诚实。** 模型接口被限流或超时，旧代码当成「答了一句空话」来扣分。表格题里「未取消」被先当成「取消」。带引号、带百分号的脏数字，出题时洗过、执行时没洗，两边对不上。还有一个「差一点也算对」的计数器先加再清零，结果恒为 0。缓存键只有题目原文，换了模型或提示词，便宜档仍可能用旧缓存假装通过。报告只留一份「最新」，跑一次便宜档会把完整档的结果盖掉。各个评测脚本一被导入就会自己接数据库；在编排环境里直接跑脚本，有机会写进线上库。

**该拒答的题被判错。** 题目明明要求「证据里没有就不要编」，模型老实拒绝了，却因为没引用文档、或者答案里没有那串数字，被算失败。事实题用裸字符串比对，短数字能误撞进长数字。

| | 改进前（正式线一带） | 改进后（这条实验线） |
|---|---|---|
| 对外能讲的成绩 | 常拿旁路套件 `yz` 的分数 | 只有整段办事 `agent` |
| 调用的代码 | 旁路：裸路由、手写表格规则、关键词检索、跳过办事流程 | 单环节打线上函数；整段办事打真实办事流程 |
| 拒答题 | 拒对了也常算失败 | 单独按「有没有拒答、有没有编造大数字」来判 |
| 事实题 | 字符串里碰上就算对 | 按结构化答案规格抽取后再比，数字要卡边界 |
| 限流、超时 | 当成空答案扣进准确率 | 评测调用会抛错，记成基础设施故障，不进准确率 |
| 报告 | 一份最新结果，便宜档盖掉完整档 | 按档各留一份；便宜档不盖掉已经通过的完整档 |
| 每次推送自动跑什么 | 缺真实数据库隔离 | 离线测试加题集检查；另有一项用普通账号测「用户之间看不见彼此的数据」 |

改动的目标就这三句：分数要测到线上那条路；判分要把「拒答」「答错」「接口坏了」分开；推代码时要有东西能拦住退步。

还没做完的，集中在第 8 节：上下文的「让模型真的作答」没有变成默认档，门禁和报告里的记账还有缺口，题集检查和离线测试也没有按方案收完。

## 2. 现在整套系统怎么串起来

所有评测套件写在一份登记册里（`backend/app/eval/suites.py`）。统一入口是 `backend/scripts/eval.py`。你敲的 `run`，由这个入口接过去跑。

一条 `run` 命令按这个顺序走：

1. 先从登记册查出这一套该怎么跑：用哪个脚本、便宜档和完整档各追加哪些参数、默认在本机虚拟环境跑还是在已经编排好的服务里跑。
2. 再决定这次实际跑在哪。命令行写的 `--target` 优先，其次是环境变量 `EVAL_TARGET`，再其次是套件自己的默认。选本机时，会强制换成一个临时数据库文件，并关掉缓存服务。选服务时，沿用编排环境已经注入的地址。
3. 开跑前先检查缺不缺东西：模型密钥、对象存储、向量库、沙箱是否健康。缺了就以退出码 2 停下，不往下跑出一次假的通过。
4. 给这次运行单独建一个目录。同一秒再跑一次会自动加后缀，避免两次写进同一个文件夹。
5. 接着真正改环境变量，并标上「已经初始化过」。同时设上 `EVAL_SKIP_ROUTER_REDIS=1`：评测不读、也不写路由用的那份共享缓存。向量和限流仍可以用共享缓存。多数单环节套件即使目标是服务，也会把应用库绑到这次运行目录里的临时库，避免评测数据写进带行级隔离的线上库。整段办事和依据核验是例外：它们要用真库，并在数据库会话上标出「当前是哪个评测用户」。
6. 开跑之前先做两件记账。一件是读上一次**同档并且通过**的报告，当作「这次退了多少」的尺子。另一件是把模型名、温度、检索开关等拍成快照。快照必须在套件自己改开关之前拍，否则报告里看到的是跑完以后的值。
7. 套件分两种跑法。若是离线测试，框架会再开一轮 pytest。若是正式评测脚本，就按登记册找到对应的 `scripts/run_*.py`，先解析命令行参数，再执行里面的运行函数。每个脚本开头仍会调一次环境初始化；若入口已经初始化过，这里直接跳过，免得把依赖库接两遍。
8. 跑完后先看有没有「没走生产路径」。完整档若自己标了这个记号，门禁直接失败。否则再用统一门禁对照绝对门槛，以及上一份同档通过的基线。任一失败，退出码至少是 1。套件自己返回 2（例如路由缓存对不上）时，不再套这道门禁，但报告照写。
9. 最后把三份结果写进这次目录：机器可读的报告、逐题样本、给人看的摘要。再按规则更新「最新」文件和总索引（写报告的代码在 `backend/app/eval/report.py`）。

档位只有两个，写在登记册里：

- **冒烟档**（命令里写 `smoke`）：便宜、尽量可重复。用来确认「这套还能跑」。多数时候不代表线上行为。
- **完整档**（命令里写 `full`）：更接近生产路径，门槛也更严。

| 套件 | 测的是什么 | 默认跑在哪 | 冒烟档实际做什么 | 完整档实际做什么 | 要什么 |
|---|---|---|---|---|---|
| `pytest` | 代码和题集约定没写坏 | 本机 | 10 个指定测试文件 | `tests/` 全量 | 无 |
| `routing` | 这句办公话该调哪些工具 | 本机 | 只回放磁盘缓存 | 刷新缓存并打模型 | 模型密钥 |
| `rag` | 检索能不能把对的文档排上来 | 本机 | 关键词对照 | 正式入库 + 关键词和向量一起搜 | 完整档要对象存储、向量库、模型密钥 |
| `tabular` | 表格题的计划和计算结果 | 本机 | 只编译计划，不进沙箱 | 模型规划 + 沙箱执行 | 完整档要沙箱和模型密钥 |
| `context` | 长对话被压缩后，关键句还在不在 | 本机 | 用规则做摘要，小切片 | 同一套逻辑，大切片 | 无。真作答要另开开关 |
| `grounding` | 依据核验有没有把回答修好或修坏 | 服务 | 少样本，跳过忠实度打分器 | 含修补前后的分差 | 模型密钥、对象存储 |
| `agent` | 整段办事做完没有 | 服务 | 按题型轮流抽大约 30 题 | 题集全量 | 模型密钥、对象存储、向量库、沙箱 |

`yz` 不在这张表里。登记册里只留了一段注释：脚本 `scripts/run_yz_eval.py` 和题集 `yz_fullchain.jsonl` 还在磁盘上，供翻旧账。登记册不再承认它，入口也拒绝 `run yz`。

## 3. 每个套件：测的是什么，代码怎么走

### 3.1 离线测试 `pytest`

测的是应用和评测基建本身，不调用付费模型。

代码怎么走：评测入口会再开一个进程，用当前的 Python 去跑测试。跑哪些文件，看登记册。冒烟档是这 10 个文件：健康检查、路由器、工具网关，以及门禁、判分、报告、统计、题集约定、整段办事助手。完整档是整个 `tests/` 目录。这个子进程默认使用临时库、关掉缓存、沙箱地址置空。跑完后从测试报告里数通过、失败、跳过，失败用例写进逐题样本。

自动流水线不经过评测入口。每次推送的「离线」任务先检查题集，再跑 `python -m pytest tests -q`（工作流文件是 `.github/workflows/eval.yml`）。另一项「数据库隔离」先用超级用户做表结构迁移，再确保存在一个普通登录账号，最后用这个普通账号 `omni_app` 跑 `tests/test_rls_postgres.py`。超级用户会绕过「强制按用户隔离」，用它测等于没测。

你怎么跑：在 `backend` 目录执行 `python -m pytest tests -q`。不用起数据库、对象存储或向量库。缺本机考勤表时，题集约定测试里「用原表重算多工具题」的那一段会跳过，并写明本机表格没参与；它前面用冻结种子做的核对已经执行过。聊天接口那组测试在没有对象存储客户端库时整文件跳过，因为应用一启动就要连存储。

### 3.2 路由 `routing`

测的是：给定一句办公话、历史，以及「有没有知识库、有没有表格」这些开关，规划这一步会点哪些工具。

代码怎么走：读入全部路由题，再逐题预测该点哪些工具。脚本在 `scripts/run_office_eval.py`，比较在 `app/eval/tool_routing.py`。题集 `data/eval/office_tool_routing.jsonl` 共 420 行。

1. 先把题目读进来。
2. 若题目带一份还没填完的日程，这里直接当成「只走日历」，不再问模型。线上办事流程在规划节点里也是这样短路的（`app/agents/workflow.py`）。
3. 否则先查磁盘缓存。缓存键不只含题目和历史，还含当前路由模型名、系统提示词的指纹、以及缓存版本。线上那份共享缓存的键现在也带上同一份提示词指纹。评测一开始就绕开它，所以完整档刷新磁盘缓存时，不会把共享缓存里的旧决策抄进 `router_cache.json`。冒烟档要求磁盘缓存必须命中：对不上就停，退出码 2，并提示先跑完整档刷新。完整档会作废旧的磁盘缓存，重新问模型，再把新决策写回磁盘。
4. 真正提问时，先把历史收成模型要用的上下文和一行摘要，再交给线上那一步「决定调哪些工具」（`app/agents/router.py` 里的 `plan_tools`）。这一步内部仍会做一次分类，但评测不再自己绕过它，所以「有没有表格」「文档范围」「那一行摘要」都会进到线上代码里。
5. 主指标是：预测的工具集合是否和标准答案完全一致。每个工具还会单独算对了多少、漏了多少。意图是从工具集合按固定顺序推出来的，另外再算一遍「用同一规则从标准工具推出来的意图」，避免两套标签互相打架。问模型时，如果碰到限流、超时，或 408、429 以及 5xx 这类传输错误（同属这一类的还有 409 和 425），会先做有限次退避重试。默认最多问两次，第一次失败后等 2 秒再试；次数若调高，等待按 2 秒、4 秒加长，最长 8 秒。次数用完仍失败，记成基础设施故障，不进入意图准确率和工具完全一致的分母，另外单独报故障占比（报告字段 `infra_error_rate`）。如果每一题都是这种故障，准确率记 0，不会因为分母空了变成满分。只有返回格式对不上（字段校验失败）才记成「出错」，留在分母里，准确率会下降，但不会被当成某种正确意图。工具先后顺序的召回仍写在报告里，不当主指标，也不进门禁。

你怎么读：这测的是规划这一步，不是整段办事。上下文由评测自己装好再传进去。线上规划节点还会排队列、决定下一个工具、给界面一个意图名，那些不在这套的计分里。

你怎么跑：`python scripts/eval.py run routing --profile smoke`。缓存文件是 `backend/data/eval/router_cache.json`。键必须对得上当前模型和提示词，对不上就明确失败，不会拿过期缓存混过去。完整档会重问模型并改写这份缓存，那一次需要模型密钥。

### 3.3 检索 `rag`

测的是：问一句，返回的文档列表里有没有标准文档、排得靠不靠前。

代码怎么走：先把语料放进库，再按每道题去检索，看标准文档有没有被排上来。脚本在 `scripts/run_rag_eval.py`，比较在 `app/eval/rag_retrieval.py`。题集 `rag_retrieval.jsonl` 共 400 行，语料在 `data/eval/corpus/rag/`。

- 冒烟档不走正式入库。它把语料里已经切好的段直接写入数据库，再调用线上的检索。此时「关键词加向量一起搜」是关着的。这种跑法会被标成关键词对照，并注明没走生产路径。这是故意的便宜对照。
- 完整档会加上「按生产方式入库」和「用重排模型」。若当前不是服务环境，直接报错，不许悄悄退回关键词、还报一个看起来不错的召回。环境对了之后，先把文件放进对象存储，再对每篇走线上入库：正式切块、做向量、写入向量库（入库函数在 `app/rag/ingestion.py`），然后同样走线上检索。向量失败，或重排退回手写规则时，会标成「生产路径降级」。评测入口见到完整档有这个记号，整次判失败。

主指标是：该找回的文档找回了多少、前几条里有没有命中、正确文档排得有多靠前（报告里这个排位指标叫 `mrr`），以及「看起来很像、其实不该命中」的那一组题。精确率仍会算进报告，并注明：标准答案只有一篇时，它会被「取前几条」卡住，所以不进主指标、不进门禁。标准答案仍是整篇文档，没有做到「哪一块才算对」。

你怎么跑：冒烟档可以在本机、不起服务：`python scripts/eval.py run rag --profile smoke`。完整档要在编排环境里跑，见第 9 节。

### 3.4 表格 `tabular`

测的是：一句话问表格，计划对不对、算出来的数对不对。

代码怎么走：先看计划写得对不对，完整档再看算出来的数对不对。脚本在 `scripts/run_office_tabular_eval.py`。题集 `office_tabular.jsonl` 共 200 行，表文件在 `data/eval/fixtures/`。冒烟切片固定 30 题。

- 冒烟档只编译计划，不进沙箱。每题用一套手写规则猜「要做求和、过滤还是连接」（规则在 `app/services/data_analysis.py`）。报告会写明：这一臂是手写规则，不代表生产上的规划能力。
- 完整档让模型来规划，再进沙箱算数。入口是线上的「分析本地表格」。只有模型真的交出了一份计划，才算规划成功。规划失败时，后面仍可能用手写规则把数算完，但这道题记为规划失败，整次运行标成没走生产路径。完整档的门禁要求规划失败率是 0，所以这种静默退回过不了。手写规则的对错另外留下，只作对照。

计划是否对上，要同时看操作类型、过滤条件、度量列、分组、连接键（比较代码在 `app/eval/office_tabular.py`）。操作类型空着，不再算通过。

以前把分数扭曲的三处，代码里已经改了：

- 认「取消」之前，先认「未取消 / 没取消 / 不含取消」（`app/services/analysis_ir.py`）。
- 沙箱读表时，和出题用的是同一套清洗：去掉引号和千分位，百分号先除以 100。出题脚本是 `gen_office_tabular_eval.py`。
- 「差一点也算对」只在真的差一点时加一。失败的题会写进报告顶层的失败列表，另有一份只留最靠前的若干条，方便人眼扫。

你怎么跑：`python scripts/eval.py run tabular --profile smoke` 不起沙箱。完整档要沙箱能应答。本机虚拟环境会去看有没有 `omni-sandbox:latest` 这张镜像；编排环境里则看沙箱服务的健康检查。

### 3.5 上下文 `context`

测的是：长对话被摘要、被截断之后，待办还在不在、拼出来的消息有没有自相矛盾、压缩到底有没有发生。现在登记册里的两个档位，都不让模型回答最后那个问题。

代码怎么走：把一段写好的长对话重放一遍，看压缩之后关键内容还在不在。脚本在 `scripts/run_context_eval.py`，回放在 `app/eval/context_replay.py`。题集 `context_recall.jsonl` 共 384 行。冒烟档和完整档都用规则摘要，并排跑「旧拼法」和「完整拼法」两臂，并打开这套自己的门禁。

每一题、每一臂这样做：

1. 按脚本把历史消息写进一次临时会话。
2. 需要刷新摘要时，走线上的「刷新会话上下文」。规则摘要档会把真正的模型摘要换成评测里的抽取式摘要，避免打模型。
3. 再用线上的组装步骤，把摘要、待办和当前问题拼成即将送给模型的消息。
4. 然后检查三件事：拼出来的消息是否自洽；待办是否还在；关键词还在不在。关键词只作诊断，这套自己的门禁和统一门禁都不卡它。
5. 「完整拼法」这一臂会把上下文长度上限压到不超过 4096，并把保留的对话轮数上限压到不超过 4，用来逼出真正的压缩。报告里同时有两件事：有没有去摘要，以及拼装时有没有真的把内容截短。统一门禁卡的是后者，下限 0.05，避免「预算很松、压缩路径从没被走到」。

这套自己的门禁还要求：自相矛盾的次数必须是 0；待办必须全部留下；用来对比的基线必须和这次是同一切片，否则拒绝比较。更新基线和打开门禁不能同一次进行，免得自己把尺子改掉再宣布通过。

让模型真作答的路径已经写了，但没有接进登记册，也没有接进自动流水线。你要手动加上 `--live`，并且先设环境变量 `RUN_CTX_EVAL=1`。不带这个变量就直接停，退出码 2。打开之后，不指定条数时会按题型轮流抽 64 题，看事实有没有回忆起来，接口故障单独记。这不是夜间定时任务，只是一条可以手开的开关。

你怎么跑：`python scripts/eval.py run context --profile smoke`。不需要服务，也不需要模型密钥。

### 3.6 依据核验 `grounding`

测的是：草稿写完之后，线上的核验和修补是把回答变得更贴证据，还是改坏了；该拒答的有没有拒。

代码怎么走：先按题目准备证据，再写草稿，然后让线上的核验决定要不要改这句草稿。脚本在 `scripts/run_grounding_eval.py`，比较在 `app/eval/grounding.py`。题集 `grounding_faithfulness.jsonl` 共 120 行，知识库、联网、沙箱三路数量接近。

每一题先准备证据。知识库题走线上检索。联网题和沙箱题用题目里冻好的证据，不真上网、不真算表。冻好的联网证据带发布日期，避免「今天」一变，过期提示就变。然后先让模型按这些证据写草稿；限流或超时会抛错，而不是交回空字符串。草稿再交给线上的核验和修补（`app/agents/harness/critique.py`）。

接口最终仍失败的题，记成基础设施故障，不进忠实度平均。题目标了「本来就答不了」时，不参与忠实度，只看拒得对不对。忠实度打分一批题只打一次，再拆成总分和逐行分（打分辅助在 `app/eval/ragas_judge.py`）。打分模型的单次输出长度上限是 2048。回答是否切题仍会算（完整档默认开着），不进门禁。冒烟档跳过这套打分，并且只取前 24 题。完整档会把修补前的草稿也打一遍，用来算「修补是抬分还是伤分」。

你怎么读：这是核验这一环的体检。证据很多是冻住的，不能当成「用户从上传到回答」的整段成绩。

### 3.7 整段办事 `agent`（唯一适合对外讲的一套）

测的是：用户的一句话（或带着历史的一轮）丢进真实办事流程之后，任务做完没有。

代码怎么走：把题目丢进和线上一样的办事流程，再看路由、证据和最终答案哪一层先坏。脚本在 `scripts/run_agent_eval.py`，驱动在 `app/eval/agent_e2e.py`。题集 `agent_tasks.jsonl` 共 174 行。方案里写的是大约 200，实际冻结下来是 174，题集约定允许的范围是 140 到 260。

一次运行做这些事：

1. 把「今天」固定成 `2026-09-19`，免得日期一变，同一份代码分数就变。同时打开「关键词加向量一起搜」和重排，和线上检索开关对齐。
2. 准备好数据库，打开一次会话，并把当前用户设成评测用户，这样行级隔离和线上一样生效。
3. 除非明确说跳过入库，否则把三份夹具放进对象存储，再按正式入库切块、做向量。三份文件都在 `backend/tests/YZ测试文档/`：制度正文、产品说明、考勤表。考勤表 `测试用例.csv` 被 git 忽略，干净检出里没有。缺任意一份，入库会直接报「文件找不到」，整次运行停住。跑完会清掉这次写入的文档。
4. 冒烟档只抽大约 30 题。抽的时候按题型、以及「有没有历史」轮流取，避免 30 题全是闲聊。
5. 每题先装好办事流程要的输入：问题、历史、有没有知识库、有没有表格、限定哪些文档、有没有未填完的日程、评测用户。然后包住工具入口：名字是联网的调用不真上网，固定返回「评测环境未联网」。沙箱、知识库、日历仍走真的入口。包着的同时记下每次工具名、有没有被拒绝、沙箱有没有算出摘要。
6. 在这个包装里进入线上的办事流程（`app/agents/workflow.py`）。流程若已经给出可以直接展示的答案，就用它。否则再用和线上聊天相同的模型，把流程留下的消息写成最终答案，并记下提示词用量。这一步若限流或超时，会抛错，不会当成空答案。

三层分开记。一道题失败时，归到最先坏的那一层：

1. **路由。** 实际执行过、且没被拒绝的工具集合，是否等于题目里写的标准工具。
2. **证据。** 看题型。事实题要引用到标准文档；若题目限定了文档范围，不能用「沙箱跑过」来顶替。计算题要沙箱真的给出摘要。多工具题要既跑了沙箱、又有引用。日历题要真的用了日历。拒答、闲聊、以及「工具根本不该出现」的题，不要求证据。
3. **完成。** 按题型看最终答案算不算做完。判的是草稿正文：会先剪掉系统追加的免责声明，避免把这段后缀当成拒答，或当成答案的一部分。

三层都过，失败层为空。路由错了记路由，否则证据错了记证据，否则记完成（结果文件里这一层的名字是 `answer`）。流程抛错时要分两种。规划阶段或作答阶段的限流、超时和同类传输错误，记成基础设施故障，不进入核心完成率的分母。字段校验失败仍记成流程错误，留在分母里。

汇总时，基础设施故障不进入「做完没有」的分母，另外给一个故障占比。完成率再附一个用重抽样估出来的区间，提醒题量不大时不要把一个点看成精确成绩（算法在 `app/eval/stats.py`）。闲聊、日历、拒答比较容易通过，所以门禁看的是核心完成率：事实、计算、多工具、以及「不该用工具」这四类。

你怎么跑：这套默认要服务。本机虚拟环境连不上对象存储和向量库时，开跑前检查会直接拒绝，并提示用编排命令。见第 9 节。

## 4. 一道题怎么算做完，失败记在哪

每道题自己带着题型。做完没有，按题型用不同规则。判分写在 `backend/app/eval/judges.py`。

- 事实题：答案要满足结构化答案规格。该答却拒了，算失败。
- 计算题：沙箱应已经执行。数字落在容差内，或满足规格。
- 拒答题：要有拒答的说法，不能编造三位及以上的数字。这类题不参与忠实度和引用扣分。
- 闲聊：不该引用知识库，路由不能明显走错。
- 日历：主要看是不是走了日历。
- 多工具：规格里的每一项都要出现。
- 工具不该出现：不该真的执行工具。要么答出规格，要么说明缺数据。

结构化答案规格常见几种：一个数字（带单位和容差）、一个时间区间、几种说法里任一即可、几项必须同时出现、一段原文必须包含。抽数字时看边界，避免短数字撞进长数字。中文数字如「十二」会先换成整数再比。

整段办事之外，其他套件用自己的失败列表，但和基础设施故障相关的约定是同一句：接口坏了不要算进「模型答错」。依据核验，以及上下文里那条手开的真作答，都会把这类故障单列。路由也一样：限流和超时先重试，重试仍失败就不进准确率的分母，并单独报故障占比；每一题都是这种故障时准确率记 0。只有字段校验失败才留在分母里，记成「出错」，准确率会下降，但不会冒充某种正确意图。整段办事里，规划阶段的限流和超时同样不进核心完成率；字段校验失败仍算流程错误。

统一门禁不认识「第几层」。它只读报告里的数字。整段办事的门槛因此写成：核心完成率有下限，基础设施故障率有上限，完整档再加一条「工具集合必须对上」的下限。这些数是门禁表里写死的地板，用来拦住明显退步，不是产品目标。过线只说明没有掉到地板以下。

## 5. 门禁和报告怎么落盘

门禁表按「哪一套、哪一档」列出门槛（表在 `backend/app/eval/gates.py`）。每条可以有绝对下限、绝对上限，以及相对上一份同档通过报告允许下跌多少。下跌默认最多 0.05；故障率这类「越低越好、但没有上一份就没法比跌幅」的指标，把下跌检查关掉。某个该有的指标从报告里消失，默认算失败，避免改代码时把字段删了还显示通过。

现在写进去的门槛是：

- 路由两档：意图准确率、工具集合完全一致的比例，下限都是 0.87。
- 检索两档：全体题目的召回下限 0.93，正确文档排位下限 0.88。另外，冒烟档和完整档都卡「看起来很像、其实不该命中」这一组：这一组的召回下限 0.95，排位下限 0.82。整体门槛没有再收紧。
- 整段办事冒烟：核心完成率下限 0.30，基础设施故障率上限 0.05。完整档核心完成率下限 0.45，工具完全一致的比例下限 0.55，故障率上限仍是 0.05。
- 依据核验冒烟只卡拒答准确率下限 0.40。完整档再加忠实度均值下限 0.70，拒答下限 0.60。
- 表格冒烟卡计划准确率下限 0.90。完整档卡执行准确率下限 0.80、需要连接的题里至少对上 10/14、规划失败率必须是 0。
- 上下文两档：自相矛盾必须是 0 次，待办必须全部留下，压缩率下限 0.05。

离线测试那一套没有写进这张门禁表。它红不红，就是测试进程自己的退出码。

报告目录默认是 `backend/reports/`，可以用环境变量 `EVAL_REPORTS_DIR` 换地方。一次运行留下：

```
reports/index.jsonl                          总索引，超过 2000 行会转成 index.jsonl.1
reports/<套件>/latest-<档位>.json             该档最近一次「可以当最新」的结果
reports/<套件>/latest-<档位>.md
reports/<套件>/latest.json                    最近一次通过的完整档；冒烟档不覆盖它
reports/<套件>/runs/<时间>_<档位>/report.json
reports/<套件>/runs/<时间>_<档位>/samples.jsonl
reports/<套件>/runs/<时间>_<档位>/summary.md
reports/<套件>/runs/<时间>_<档位>/stdout.log
```

「这一档的最新」只在两种情况下被换掉：这次退出码是 0，或者这个档还没有任何最新文件。失败的运行仍留在按时间分的目录里，但不会变成别人眼中的「最新」，也不会变成下一次比较退步的尺子。找尺子时，会往回找同档里最后一次退出码为 0 的报告。

每份报告的抬头记着：套件、档位、跑在本机还是服务、命令行、开始时间、耗时、代码版本、题集路径和内容指纹、相关输入文件的指纹、开跑前的设置快照、运行中的计数、退出码、目录。代码版本优先读环境变量 `GIT_SHA`，否则在本机问 git。编排文件把这个变量透传进容器了，但容器里没有仓库历史；你不在外面导出它，容器里会记成 `unknown`。

输入指纹总会带上 `data/eval/fixtures` 里的表格夹具。检索再带语料目录。整段办事和依据核验再带 `data/eval/seeds` 里的种子。被忽略的本机考勤表不在这条清单里。

整段办事的运行计数里有：故障题数、延迟的平均值和中间水平、能测到的提示词用量。入口还会并入一次「这次进程里所有补全调用」的累计：次数、重试、基础设施故障、延迟和用量。不是每一套都有逐题延迟。

对比同一套、同一档最近两次运行：`python scripts/eval.py diff <套件> --profile full`。它按目录名取出最后两份报告，用失败题的编号做差，打印新挂的和新修好的。只看最近一份给人读的摘要：`python scripts/eval.py last <套件> --profile smoke`。不写档位时，读的是「最近一次通过的完整档」。

## 6. 题集从哪来，约定查什么

题集是生成器写出来的，不靠模型现场编题。

- 路由题由 `scripts/gen_office_eval.py` 写出。名字里带 `500` 的那个文件只是转调它的旧入口。
- 检索题由 `scripts/gen_rag_eval.py` 写出。带 `500` 的同样是旧入口。
- 表格题和夹具由 `scripts/gen_office_tabular_eval.py` 写出，标准答案用清洗后的表重算。
- 上下文回放题由 `scripts/gen_context_eval.py` 写出。
- 依据核验题由 `scripts/gen_grounding_eval.py` 写出，证据来自审过的种子。
- 整段办事题由 `scripts/gen_agent_eval.py` 写出。
- 已下线套件的历史题集由 `scripts/gen_yz_eval.py` 写出，只供翻旧账。

考勤类数字若本机有 `backend/tests/YZ测试文档/测试用例.csv`，生成器会按表重算。这份文件被忽略，仓库和自动流水线默认没有。没有它时，整段办事的生成器改读 `data/eval/seeds/yz_attendance.jsonl` 里冻住的数。

检查入口是 `python scripts/lint_eval_datasets.py`。它做两件事：按每套题集自己的约定检查一遍，再检查套件之间的标签是否一致（约定写在 `app/eval/contracts.py`）。

每套自己的检查看：字段形状对不对、行数在不在允许范围、去掉标点后有没有重复题、分布是否离谱。另外还要求：登记册里每个带题集的套件都有一份约定，约定里也不许多出已经下线的名字。`yz` 故意不在这份约定清单里。

整段办事还有几条硬规定：多轮题要占一定比例，特别短的问法不能太多，同一个意思的问法不能超过两种，拒答题不能带着标准文档或答案规格，事实题和计算题必须有规格和标准文档，考勤汇总必须路由到沙箱，开关不能和标准工具打架。

跨题集检查看路由题和办事题：标了沙箱就必须声明「有表格」，标了知识库就必须声明「有文档」，办事题上写的意图必须和「从工具集合按同一规则推出来的意图」一致。历史 `yz` 题若和这条约定冲突，只打印警告，不让检查失败。

「答案规格能不能从原文或表格重算出来」没有放进约定文件本身。它落在测试 `tests/test_eval_datasets_contract.py`：汇总题对照冻结种子；多工具题在本机考勤表存在时对照重算结果，不存在就跳过。

测试标记在 `pytest.ini` 里定义了三类：不连外部的、要本地应用的、会打到真模型或真服务的。目前只有评测基建的少数测试，以及数据库隔离测试，打了这些标记，并没有覆盖全部测试文件。

聊天接口有一条不拆掉办事流程的测试，在 `tests/test_chat_sse_routing.py`。它用固定的假模型回复替换真实模型，然后真的打聊天接口。同一文件里其他用例仍会把整个办事流程换成假的。整份文件在缺少对象存储客户端库时跳过。编排文件里的评测服务已经把 `backend/tests` 挂进容器。

## 7. 走一遍：离线测试，再走一遍评测入口

下面两段都不需要启动数据库、对象存储、向量库或沙箱。工作目录是仓库里的 `backend`。

### 7.1 离线测试，和自动流水线同一条命令

```bash
cd backend
python scripts/lint_eval_datasets.py
python -m pytest tests -q
```

第一行检查六套现役题集的字段和分布，再检查套件之间的标签是否一致。某一套失败会打印具体是哪一行、为什么，进程以退出码 1 结束。

第二行就是自动流水线里「离线」任务的测试步骤。流水线还会先设好临时库地址、关掉缓存、把沙箱地址清空。测试收集 `tests/` 下的用例。判分、门禁、报告、路由里不联网的部分、表格清洗，这些不需要外部服务。数据库隔离那份测试发现当前不是它要的数据库时会跳过；那一项由流水线的另一项任务单独跑。没有本机考勤表时，多工具题的重算会跳过。没有对象存储客户端库时，聊天接口那份文件会跳过。

看某一小块也可以，例如只看判分：

```bash
python -m pytest tests/test_eval_judges.py -q
```

这条只检查「怎样算做完」和数字边界，仍然不连模型。

### 7.2 评测入口，以上下文冒烟档为例

```bash
cd backend
python scripts/eval.py run context --profile smoke
```

入口认出套件是上下文、档位是冒烟，没有额外参数。然后按第 2 节的顺序做：

1. 从登记册拿到这套的脚本，以及冒烟档要附加的参数：用规则做摘要、只取冒烟切片、并排跑旧拼法和完整拼法、打开这套自己的门禁。默认跑在本机。这套开跑前不要求密钥或外部服务，检查通过。
2. 建好这次的目录，形如 `reports/context/runs/<时间>_smoke/`。
3. 把数据库指到这次目录里的临时文件，关掉缓存，清空沙箱地址，把「今天」冻住。
4. 因为这套在本机不需要真的对象存储，就装一个什么都不存的替身，避免启动时去连存储。
5. 记下上一份通过的基线和当前设置，并把「这次模型调用了多少次」的计数清零。
6. 找到上下文的评测脚本，解析上面那些档位参数，开始回放。
7. 回放前先确认没有同时要求「改写基线」和「按基线判过不过」。然后读出冒烟切片，对每题、每一臂重放一遍拼装，再用这套自己的门禁看自洽和待办。这一关失败时，退出码已经是 1。
8. 回到入口。这次没有标成「没走生产路径」，于是再用统一门禁查三条：自相矛盾的次数、待办有没有留住、压缩有没有发生。失败同样把退出码抬到 1。
9. 把报告写盘。终端最后两行是这次报告的路径，和这一档「最新」文件的路径。

想看刚才那份，而不必打开文件：

```bash
python scripts/eval.py last context --profile smoke
```

同一条入口换套件时，只有「真正开始评测」那一步换内容。检索冒烟走关键词对照，不按生产入库。表格冒烟只编译手写计划，不进沙箱。这两条同样不用起服务：

```bash
python scripts/eval.py run rag --profile smoke
python scripts/eval.py run tabular --profile smoke
python scripts/eval.py run pytest --profile smoke
```

`eval.py run pytest --profile smoke` 和直接 `pytest tests -q` 不是同一范围：前者只跑登记册里那 10 个文件，后者跑整个 `tests/`。自动流水线用的是后者。

## 8. 对照改进方案：做完了、做了一部分、还没做

方案原文把七步标成五项已完成、三项未完成。下面按当前代码重判，不按方案文件头上的勾选。

**已完成**

- 让分数失真的缺陷。限流和超时在评测调用里会先重试，最终仍失败就抛错，记成基础设施故障，不进准确率。路由这一套现在也这样：408、429、5xx 这类传输错误先退避重试，次数用完就不进意图准确率和工具完全一致的分母，并单独报故障占比；全部都是这种故障时准确率记 0。只有字段校验失败还算「出错」，留在分母里。整段办事里，规划阶段的同类故障同样不进核心完成率，字段校验失败仍算流程错误。普通业务调用如果没有打开「失败就抛错」，仍可能得到空字符串，那是线上兜底，不是评测计分这条路。表格里否定词的先后、脏数字清洗、「差一点也算对」的计数、按档保留最新报告，都已经落在第 3 节写过的位置。路由的磁盘缓存和线上共享缓存，键里都带上提示词指纹。评测会绕开路由共享缓存，完整档刷新时不会把旧决策写进磁盘缓存。各个评测脚本被导入时仍会试一次环境初始化，但入口先做过之后，这一下会跳过。各套件也标明了：要不要把应用库改绑到临时文件。
- 判分改造。拒答单独判，事实题用结构化答案规格，路由和检索换了主指标，依据核验一批题只打一次分，回答是否切题不进门禁，「今天」被冻住，冻住的联网证据带发布日期。工具先后顺序的召回仍写在路由报告里，只是退出了主指标和门禁。检索的标准答案仍是整篇文档，方案里可选的「哪一块才算对」没有做。
- 单环节改打线上路径。路由走规划函数，并带上上下文和「未填完的日程直接走日历」。检索的完整档走正式入库，再加上关键词和向量一起搜；退回纯关键词会判失败。表格的完整档走「让模型规划再进沙箱」。依据核验走线上的核验和修补。
- 题集重建。六套现役题集都在，行数见第 2 节的表和第 3 节。拒答题不带标准文档，考勤汇总标成走沙箱。历史 `yz` 题集还在，只供对照。
- 整段办事套件，以及从登记册移除 `yz`。失败分成路由、证据、完成三层，联网用固定回复代替，日期被冻住。规划阶段的限流和超时记成基础设施故障，不进核心完成率。题量是 174，不是方案草稿里的大约 200。

**做了一部分**

- 上下文的指标，以及让模型真作答。规则摘要、自洽检查、待办、压缩和摘要分开计数、压低长度上限、同一切片才许比基线、禁止「改基线」和「按基线判过不过」一起开，这些已经有了。让模型作答的开关也能开，但要手设 `RUN_CTX_EVAL=1`，不在登记册的冒烟档或完整档里，自动流水线也不跑它。因此现在的上下文分数回答的是「拼得对不对」，不是「答得对不对」。
- 统一门禁和报告。门槛表、按档留最新、对比两次运行、开跑前的设置快照、输入指纹、运行目录遇到重名就加后缀、写「最新」时先写临时文件再替换、总索引太长就轮转、整段办事的重抽样区间和逐题延迟，都有。检索的冒烟档和完整档都加上了难负例这一组的门槛：召回不低于 0.95，排位不低于 0.82；全体题目的门槛仍是 0.93 和 0.88。缺口是：离线测试不在门槛表里；重抽样区间只做了整段办事的完成率，没有铺到每一套会花钱的评测；逐题延迟和用量主要在整段办事，其他套件最多有整次运行的累计；容器里的代码版本要你在外面导出，否则记成未知；被忽略的本机考勤表本身不进输入指纹。方案里「同一段代码跑两次，差别落在区间里」没有做成自动检查。
- 题集约定和离线测试。约定清单已经跟登记册对齐。跨题集标签、去重、多轮和超短问法、拒答不带标准文档，都有。行级隔离的测试，以及「用普通账号跑」的流水线任务，也有了。假模型、一条不拆掉办事流程的聊天测试、三类测试标记的定义、编排环境挂上测试目录，也都有。缺口是：答案规格的重算只在一条测试里，而且缺本机表会跳过；标记没有打到大部分测试上；聊天测试文件里多数用例仍把办事流程换成假的，并且整文件依赖对象存储客户端库。

**还没做**

- 没有夜间定时去跑上下文的真作答。代码里的开关不等于已经排进日程。
- 没有让每一套会打模型的评测都带上重抽样区间。
- 没有在题集约定里，对全部答案规格按语料或表格重算一遍。

对外只讲整段办事的完成情况，并写上档位、题量、区间，以及基础设施故障有多少。冒烟档、纯关键词检索、手写表格计划、规则摘要，都不能当这条成绩。

## 9. 本机不想启动服务时，可以跑什么

都在 `backend` 目录。不需要数据库、对象存储、向量库、沙箱进程。

```bash
python scripts/eval.py list
python scripts/lint_eval_datasets.py
python -m pytest tests -q
python scripts/eval.py run pytest --profile smoke
python scripts/eval.py run rag --profile smoke
python scripts/eval.py run tabular --profile smoke
python scripts/eval.py run context --profile smoke
python scripts/eval.py last context --profile smoke
```

路由冒烟不连服务，但要一份对得上当前模型和提示词的缓存。没有就不要指望它通过。按它打印的提示去跑完整档，而那一次需要模型密钥。

下面这些会在开跑前检查，或在套件内部停下来，直到服务和密钥齐：

```bash
python scripts/eval.py run agent --profile smoke
python scripts/eval.py run grounding --profile smoke
python scripts/eval.py run rag --profile full
python scripts/eval.py run tabular --profile full
```

整段办事入库还要那三份夹具都在磁盘上。干净检出里只有制度正文和产品说明，考勤表不在仓库里。文件缺失时跑不起来，和服务没起来是两件不同的事。

服务和夹具都齐了以后，用编排环境跑：

```bash
export GIT_SHA=$(git rev-parse --short HEAD)
docker compose --profile eval run --rm eval \
  python scripts/eval.py run agent --profile smoke
```

名叫 `eval` 的这个服务默认不随普通启动拉起。它要等数据库、缓存、向量库、对象存储和沙箱都健康，并把应用代码、脚本、数据和测试目录挂进去。应用库会不会改绑到临时文件，仍看这一套的登记：整段办事和依据核验用真库。

自动流水线里，每次推送和拉取请求跑两项：不连外部的测试，以及用普通账号做的数据库隔离。要模型或整套服务的套件不在每次推送里。只有手动触发工作流时，才会再跑一轮不花钱的冒烟：离线测试、检索、表格、上下文。
