# 评测系统白话说明

这份说明只讲三件事：测的是什么、代码怎么走、你怎么跑。

对照的是正式线 `release` 上的旧评测，和当前实验线 `wip/eval-snapshot-1010`（提交 `6d927a8`）。正式线没有被这条实验线改掉。文里不写实测分数。代码里的及格线会标明是「门槛」，不是「这次跑出来的成绩」。

先记住三句：

- 离线测试不花钱、不连大模型，用来看代码和题目有没有写坏。
- 单环节测试分别打路由、检索、表格、上下文、依据核验，而且要打到线上真正用的函数。
- 整段办事只有一套适合拿去对外讲。代码里叫 `agent`。旧的旁路套件 `yz` 已经从注册表拿掉，不要再引用它的分数。

读的时候，一个技术名字第一次出现会在括号里用白话说一遍。后面尽量只用白话。

---

## 1. 改之前出了什么问题，改之后变成什么样

旧评测的毛病可以收成三类。

**走错了路。** 很多分数测的不是用户真正会碰到的代码。路由直接叫旧的 `route()`，绕过了线上规划。检索一直关掉混合检索，也没有按正式入库切块。表格测的是一套手写规则，不是线上那个让模型来规划的函数。整段问答绕开了真正的办事流程。

**分数不诚实。** 模型接口被限流或超时，旧代码当成「答了一句空话」来扣分。表格题里「未取消」被先当成「取消」。带引号、带百分号的脏数字，出题时洗过、执行时没洗，两边对不上。还有一个软通过计数器先加再清零，结果恒为 0。缓存键只有题目原文，换了模型或提示词，冒烟档仍可能用旧缓存假装通过。报告只留一份「最新」，跑一次便宜档会把完整档的结果盖掉。各个 `run_*.py` 一被导入就会自己接数据库；在编排环境里直接跑脚本，有机会写进线上库。

**该拒答的题被判错。** 题目明明要求「证据里没有就不要编」，模型老实拒绝了，却因为没引用文档、或者答案里没有那串数字，被算失败。事实题用裸字符串比对，短数字能误撞进长数字。

| | 改进前（正式线一带） | 改进后（这条实验线） |
|---|---|---|
| 对外能讲的成绩 | 常拿旁路套件 `yz` 的分数 | 只有整段办事 `agent` |
| 调用的代码 | 旁路：裸路由、手写表格规则、关键词检索、跳过办事流程 | 单环节打生产函数；整段办事打 `run_agent_workflow` |
| 拒答题 | 拒对了也常算失败 | 单独按「有没有拒答、有没有编造大数字」来判 |
| 事实题 | 字符串里碰上就算对 | 按结构化答案规格抽取后再比，数字要卡边界 |
| 限流、超时 | 当成空答案扣进准确率 | 评测调用会抛错，记成基础设施故障，不进准确率 |
| 报告 | 一份最新结果，便宜档盖掉完整档 | 按档各留一份；便宜档不盖掉已经通过的完整档 |
| 每次推送自动跑什么 | 缺真实数据库隔离 | 离线测试加题集检查；另有一项用普通账号测行级隔离 |

改动的目标就这三句：分数要测到线上那条路；判分要把「拒答」「答错」「接口坏了」分开；推代码时要有东西能拦住退步。

还没做完的，集中在第 8 节：上下文的「让模型真的作答」没有变成默认档，门禁和报告元数据还有缺口，题集契约和离线测试也没有按方案收完。

## 2. 现在整套系统怎么串起来

所有评测套件登记在 `backend/app/eval/suites.py` 的 `SUITES`。统一入口是 `backend/scripts/eval.py`。你敲的 `run`，最后进 `_cmd_run`。

一条 `run` 命令按这个顺序走：

1. `get_suite` 从注册表取出这一套的说明：要调哪个脚本、冒烟档和完整档各追加哪些参数、默认在本机虚拟环境跑还是在编排好的服务里跑。
2. `pick_target` 决定跑在哪。命令行 `--target` 优先，其次是环境变量 `EVAL_TARGET`，再其次是套件自己的默认。虚拟环境会强制用临时数据库文件，并关掉缓存服务。服务目标沿用编排环境注入的地址。
3. `preflight` 先看缺什么。缺模型密钥、对象存储、向量库或沙箱健康检查失败，直接退出码 2，不往下跑出假绿。
4. `make_run_dir` 建这次运行的目录。同一秒再跑一次会自动加后缀，避免两次写进同一个文件夹。
5. `bootstrap` 真正改环境变量，并写上 `EVAL_BOOTSTRAPPED=1`。多数单环节套件即使目标是「服务」，也会把应用库绑到这次运行目录里的临时库（参数 `isolate_app_db=True`），避免评测数据写进带行级隔离的线上库。整段办事和依据核验这两个套件例外，它们要用真库，并在库会话上设置当前用户。
6. 开跑之前先做两件记账：`read_baseline` 读上一次**同档并且通过**的报告，当作「退了多少」的尺子；`settings_snapshot_safe` 把模型名、温度、检索开关等拍下来。必须在套件自己改开关之前拍，否则报告里看到的是跑完以后的值。
7. 套件若是离线测试，走 `_run_pytest`，拉起一次 `pytest`。否则 `load_suite_module` 导入注册表里的那个 `scripts/run_*.py`，先 `build_parser`，再 `run`。各脚本文件开头仍会调用 `ensure_bootstrap`：入口已经引导过时，这一下什么都不做，避免接两次库。
8. 跑完后，完整档若报告自己标了 `degraded`（没走生产路径），`_degradation_reason` 直接判门禁失败。否则 `evaluate_gates`（在 `backend/app/eval/gates.py`）对照绝对门槛和上一份通过的基线。任一失败把退出码抬到至少 1。套件自己返回 2（例如路由缓存缺失）时，不再套门禁，但报告照写。
9. `write_run`（在 `backend/app/eval/report.py`）把 `report.json`、`samples.jsonl`、`summary.md` 写进这次目录，并按规则更新「最新」文件和总索引。

档位只有两个，在注册表的 `profiles` 里：

- **冒烟档**（命令里写 `smoke`）：便宜、尽量可重复。用来确认「这套还能跑」。多数时候不代表线上行为。
- **完整档**（命令里写 `full`）：更接近生产路径，门槛也更严。

| 套件 | 测的是什么 | 默认跑在哪 | 冒烟档实际做什么 | 完整档实际做什么 | 要什么 |
|---|---|---|---|---|---|
| `pytest` | 代码和契约没写坏 | 本机 | 10 个指定测试文件 | `tests/` 全量 | 无 |
| `routing` | 这句办公话该调哪些工具 | 本机 | 只回放磁盘缓存 | 刷新缓存并打模型 | 模型密钥 |
| `rag` | 检索能不能把对的文档排上来 | 本机 | 关键词对照 | 正式入库 + 混合检索 | 完整档要对象存储、向量库、模型密钥 |
| `tabular` | 表格题的计划和计算结果 | 本机 | 只编译计划，不进沙箱 | 模型规划 + 沙箱执行 | 完整档要沙箱和模型密钥 |
| `context` | 长对话被压缩后，关键句还在不在 | 本机 | 规则摘要，小切片 | 同一套逻辑，大切片 | 无。真作答要另开开关 |
| `grounding` | 依据核验有没有把回答修好或修坏 | 服务 | 少样本，跳过忠实度打分器 | 含修补前后的分差 | 模型密钥、对象存储 |
| `agent` | 整段办事做完没有 | 服务 | 分层抽大约 30 题 | 题集全量 | 模型密钥、对象存储、向量库、沙箱 |

`yz` 不在这张表里。`suites.py` 里只留了一段注释：脚本 `scripts/run_yz_eval.py` 和题集 `yz_fullchain.jsonl` 还在磁盘上，供翻旧账，注册表不再承认它，入口也拒绝 `run yz`。

## 3. 每个套件：测的是什么，代码怎么走

### 3.1 离线测试 `pytest`

测的是应用和评测基建本身，不调用付费模型。

代码怎么走：`eval.py` 的 `_run_pytest` 用当前解释器执行 `python -m pytest`，路径来自注册表。冒烟档是这 10 个文件：`test_health.py`、`test_router.py`、`test_harness_gateway.py`，以及门禁、判分、报告、统计、题集契约、整段办事助手的测试。完整档是整个 `tests/`。子进程里默认使用临时库、关掉缓存、沙箱地址置空。结果从 `junit.xml` 数通过、失败、跳过，失败用例写进 `samples`。

自动流水线不经过 `eval.py`。`.github/workflows/eval.yml` 的 `offline` 任务直接跑 `python scripts/lint_eval_datasets.py`，再跑 `python -m pytest tests -q`。另一项 `rls` 先用超级用户做数据库迁移，再调用 `ensure_app_role()`，最后用普通账号 `omni_app` 跑 `tests/test_rls_postgres.py`。超级用户会绕过强制行级隔离，用它测等于没测。

你怎么跑：在 `backend` 目录执行 `python -m pytest tests -q`。不用起数据库、对象存储或向量库。缺本机考勤表时，`tests/test_eval_datasets_contract.py` 里核对多工具题数字的那一段会 `pytest.skip`，并写明本机表格没参与；它前面用冻结种子做的核对已经执行过。聊天接口那组测试在没有 `boto3` 时整文件跳过，因为应用启动要连对象存储客户端。

### 3.2 路由 `routing`

测的是：给定一句办公话、历史和「有没有知识库 / 表格」这些开关，规划函数会点哪些工具。

代码怎么走：

1. `scripts/run_office_eval.py` 的 `run` 读题集 `data/eval/office_tool_routing.jsonl`（420 行），调用 `app/eval/tool_routing.py` 的 `run_tool_routing_eval`。
2. 每题进 `predict_case`。若题目带未填完的日程（`pending_calendar`），这里直接短路成「只走日历」，不再问模型。这是照着生产代码 `app/agents/workflow.py` 里 `plan_node` 的同一段短路写的。
3. 否则先查磁盘缓存。缓存键在 `_cache_key`：除了题目和历史，还有 `router_fingerprint()`，里面是路由模型名、系统提示词的哈希、缓存版本号。冒烟档带 `--require-cache`。键对不上就抛 `CacheMissError`，`run` 返回退出码 2，提示先跑完整档刷新。完整档带 `--refresh-cache`，缓存作废，重新问模型。
4. 真正提问时，先 `build_context` 得到历史和一行上下文摘要，再调用生产函数 `app/agents/router.py` 的 `plan_tools`。`plan_tools` 内部仍会调用 `route()`，但评测不再自己直接调 `route()`，因此「有没有表格」「文档范围」「上下文那一行」都会进到生产函数里。
5. 工具集合是否和标准答案完全一致，是主指标。逐个工具标签的精确率、召回率也会汇总。意图是从工具集合按固定顺序推出来的（`intent_from_decision`），另有一个「按同一规则从标准工具推导」的对照准确率，避免两套标签互相打架。模型出错记成 `error`，进混淆矩阵，不会被当成某种意图蒙混过关。工具顺序的轨迹召回仍写在报告字段 `trajectory_recall_at_k` 里，不当主指标，也不进门禁。

你怎么读：这测的是规划函数，不是整段办事。上下文由评测自己用 `build_context` 装好再传进去，线上 `plan_node` 还会做队列、下一工具、意图展示，那些不在这套的计分里。

你怎么跑：`python scripts/eval.py run routing --profile smoke`。缓存文件是 `backend/data/eval/router_cache.json`。键必须对得上当前模型和提示词，对不上就明确失败，不会拿过期缓存混过去。完整档会重问模型并改写这份缓存，那一次需要模型密钥。

### 3.3 检索 `rag`

测的是：问一句，返回的文档列表里有没有标准文档、排得靠不靠前。

代码怎么走：`scripts/run_rag_eval.py` 的 `run` 调 `app/eval/rag_retrieval.py` 的 `run_rag_retrieval_eval`。题集 `rag_retrieval.jsonl` 共 400 行，语料在 `data/eval/corpus/rag/`。

- 冒烟档不带 `--production`。`seed_eval_corpus` 按语料里已切好的段直接写入数据库，再调用生产检索函数 `app/rag/retrieval.py` 的 `retrieve`。混合检索开关被关掉。`classify_rag_run` 把这种跑法标成 `keyword_paragraph`，并且 `degraded=true`。这是故意的对照，不是线上检索。
- 完整档注册表会加上 `--production` 和 `--zhipu-rerank`。`run` 发现当前目标不是服务，直接抛错，不许悄悄退回关键词还报一个看起来不错的召回。目标是服务时，`seed_eval_corpus_production` 把文件放进对象存储，再对每篇调用生产入库 `app/rag/ingestion.py` 的 `ingest_document`（正式切块、向量、写入向量库），然后同样走 `retrieve`。向量失败或重排退回规则时，`classify_rag_run` 标 `production_degraded`。`eval.py` 见到完整档的 `metrics.degraded` 为真，整次判失败。

主指标是召回、命中、正确文档排得有多靠前（报告字段 `mrr`），以及「难负例」这一切片。精确率仍算进报告，并注明单文档题上它被「取前几条」卡住，不进主指标、不进门禁。标准答案仍是文档级的 `gold_doc_keys`，没有做到「哪一块才算对」。

你怎么跑：冒烟档可以在本机、不起服务：`python scripts/eval.py run rag --profile smoke`。完整档要在编排环境里跑，见第 9 节。

### 3.4 表格 `tabular`

测的是：一句话问表格，计划对不对、算出来的数对不对。

代码怎么走：`scripts/run_office_tabular_eval.py` 的 `run`。题集 `office_tabular.jsonl` 共 200 行，表文件在 `data/eval/fixtures/`。冒烟切片固定 30 题。

- 冒烟档 `--dry-compile`。`eval_plan` 对每题调用 `_plan_spec`，里面是 `app/services/data_analysis.py` 的 `_heuristic_spec`（手写规则）。不进沙箱。报告里的 `plan_arm` 写成 `heuristic`，并注明这不代表生产规划。
- 完整档 `--planner llm`。`eval_exec` 调生产入口 `analyze_local_tables(..., planner="llm")`。这个函数内部在规划阶段调用 `_plan_analysis_spec`。只有返回的 `plan_source == "llm"` 才算模型规划成功。失败时执行仍可能用手写规则把数算完，但该题记 `planner_error`，`plan_ok` 为假，整次报告 `degraded=true`。完整档因此过不了门禁：规划失败率的上限是 0。手写规则保留为对照臂，字段是 `heuristic_plan_ok`。

计划是否匹配看 `app/eval/office_tabular.py` 的 `plan_matches`：操作类型、过滤、度量列、分组、连接键都要和标准计划对上。操作类型空着不再算通过。

以前把分数扭曲的三处，代码里已经改了：

- `app/services/analysis_ir.py` 先认「未取消 / 没取消 / 不含取消」，再认「取消」。
- 沙箱里执行用的 `load_frames` 走 `clean_loaded_frame`。百分号会除以 100。出题脚本 `gen_office_tabular_eval.py` 用同一个清洗家族里的 `clean_sales_frame`。
- `aggregate_report` 里软通过计数只在 `soft_exec_ok` 为真时加一。失败行写入顶层 `failures`，同时也保留 `top_failures`。

你怎么跑：`python scripts/eval.py run tabular --profile smoke` 不起沙箱。完整档要沙箱能应答，本机虚拟环境会去看有没有 `omni-sandbox:latest` 这张镜像；编排环境里则看沙箱服务的健康检查。

### 3.5 上下文 `context`

测的是：长对话被摘要、被截断之后，待办还在不在、不变量破没破、压缩到底有没有发生。现役档位不让模型回答最后那个问题。

代码怎么走：`scripts/run_context_eval.py` 的 `run` 调 `app/eval/context_replay.py` 的 `run_context_eval`。题集 `context_recall.jsonl` 共 384 行。注册表的冒烟档和完整档都是 `--summarizer extractive`，两臂是 `legacy` 和 `full`，并带上套件自己的 `--gate`。

每一题、每一臂进 `replay_case`：

1. 按脚本把历史消息写进一次临时会话。
2. 需要刷新摘要时调用生产函数 `refresh_session_context`。规则摘要档会把 `summarize_incremental` 换成评测里的抽取式摘要，避免真的打模型。
3. 用生产函数 `build_context` 组装上下文，再用 `compose_answer_messages` 拼出即将送给模型的消息。
4. `check_invariants` 查拼出来的消息是否自洽。`pending_retention` 看待办是否还在。`needle_presence` 看关键词还在不在，只作诊断。`gate_report` 里写明它不进这套自己的门禁；统一门禁表里也没有它。
5. `full` 这一臂会把上下文长度上限压到不超过 4096，并把保留的对话轮数上限压到不超过 4，用来逼出真正的压缩。报告里同时有 `summary_rate`（有没有去摘要）和 `compaction_rate`（拼装时有没有真的截短）。统一门禁卡的是压缩率，下限 0.05，避免「预算很松、压缩路径从没被走到」。

套件自己的 `gate_report` 还会做这些事：不变量必须为 0；待办保留必须是满分；基线文件的切片名必须和这次相同，否则拒绝比较；`--update-baseline` 和 `--gate` 不能同时开。

让模型真作答的路径已经写了，但没有接进注册表，也没有接进自动流水线。你要手动加 `--live`，并且环境变量 `RUN_CTX_EVAL=1`。不带这个变量，`run` 直接退出码 2。打开之后，不指定条数时会按题型轮流抽 64 题，计 `fact_recall`，基础设施故障单独记。这不是夜间定时任务，只是一条可以手开的开关。

你怎么跑：`python scripts/eval.py run context --profile smoke`。不需要服务，也不需要模型密钥。

### 3.6 依据核验 `grounding`

测的是：草稿写完之后，生产上的核验和修补是把回答变得更贴证据，还是改坏了；该拒答的有没有拒。

代码怎么走：`scripts/run_grounding_eval.py` 的 `run` 调 `app/eval/grounding.py` 的 `run_grounding_eval`。题集 `grounding_faithfulness.jsonl` 共 120 行，知识库、联网、沙箱三路数量接近。

每题 `build_evidence_for_case`：知识库题会 `retrieve`；联网和沙箱题用题目里冻好的证据，不真上网、不真算表。冻好的联网证据带 `publish_date`，避免「今天」一变，过期提示就变。然后 `generate_grounded_answer`：先用 `complete_text(..., raise_on_error=True)` 写草稿，再调用生产函数 `app/agents/harness/critique.py` 的 `ground_and_repair_answer`。

限流或超时变成 `LLMInfraError`，该题 `infra_error=true`，不进忠实度平均。题目标了 `expect_unanswerable` 时，不参与忠实度，只看 `is_refusal` 拒得对不对。忠实度打分走 `app/eval/ragas_judge.py` 的 `run_ragas_rows`：一批题只调用一次 `evaluate()`，再用 `to_pandas()` 拆成总分和逐行分。打分模型设了 `max_tokens=2048`。相关性分数仍会算（完整档默认开着），不进门禁。冒烟档是 `--skip-ragas --limit 24`。完整档加 `--score-drafts`，用来算修补前后的差值 `repair_delta`。

你怎么读：这是核验这一环的体检。证据很多是冻住的，不能当成「用户从上传到回答」的端到端成绩。

### 3.7 整段办事 `agent`（唯一适合对外讲的一套）

测的是：用户的一句话（或带着历史的一轮）丢进真实办事流程之后，任务做完没有。

代码怎么走：`scripts/run_agent_eval.py` 的 `run` 调 `app/eval/agent_e2e.py` 的 `run_agent_eval`。题集 `agent_tasks.jsonl` 共 174 行。方案里写的是大约 200，实际冻结下来是 174，契约允许的范围是 140 到 260。

`run_agent_eval` 做这些事：

1. 把「今天」设成 `2026-09-19`（环境变量 `EVAL_TODAY`，`bootstrap` 里也会设一次）。打开混合检索和重排，和线上检索开关对齐。
2. `init_db` 后打开会话，`set_rls_context` 把当前用户设成评测用户。
3. 除非 `--skip-ingest`，否则 `seed_yz_corpus`（在 `app/eval/yz_fullchain.py`）把三份夹具放进对象存储，再对每份调用生产入库 `ingest_document`。三份文件都在 `backend/tests/YZ测试文档/`：制度正文、产品说明、考勤表。考勤表 `测试用例.csv` 被 git 忽略，干净检出里没有。缺任意一份，`seed_yz_corpus` 直接抛 `FileNotFoundError`，整次运行停住。跑完后 `clear_yz_corpus` 清掉这次写入的文档。
4. 冒烟档注册表带 `--limit 30`。`stratified_sample` 按题型和「有没有历史」轮流抽，避免 30 题全是闲聊。
5. 每题 `run_task`。它先用 `workflow_kwargs` 装好参数：问题、历史、有没有知识库、有没有表格、文档编号、未填完的日程、评测用户。然后 `trace_gateway` 包住工具网关 `gateway.invoke`：名字是 `web` 的调用不联网，固定返回「评测环境未联网」。沙箱、知识库、日历仍走真的网关。包着的同时记下每次工具名、是否被拒绝、沙箱有没有算出摘要。
6. 在这个包装里调用生产入口 `app/agents/workflow.py` 的 `run_agent_workflow`。返回里若已有 `direct_answer` 就用它；否则用 `complete_text_with_usage(..., model=resolved_chat_model(), raise_on_error=True)` 把流程留下的消息写成最终答案，并记下提示词消耗的词元数。

三层分开记，失败归到最先坏的那一层（字段 `failed_layer`）：

1. **路由。** 实际执行过、且没被拒绝的工具集合，是否等于题目里的 `route_gold.tools`。对了记 `routing_ok`。
2. **证据。** 看题型。事实题要引用到标准文档（若题目限定了文档范围，不能用「沙箱跑过」来顶替）。计算题要沙箱真的给出摘要。多工具题要既跑了沙箱、又有引用。日历题要真的用了日历。拒答、闲聊、以及「工具根本不该出现」的题，不要求证据。
3. **完成。** `judges.judge_completion` 按题型判最终答案。判的是草稿正文：`strip_grounding_disclaimer` 会先剪掉生产代码追加的免责声明，避免把系统后缀当成拒答或当成答案。

三层都过，`failed_layer` 为空。路由错了记 `routing`，否则证据错了记 `evidence`，否则记 `answer`。流程抛错时，若异常链上能找到 `LLMInfraError`，记 `infra_error`；其他异常记 `workflow_error`。

`aggregate` 把 `infra_error` 从「做完没有」的分母里拿掉，单独给 `infra_error_rate`。完成率另附一次重抽样得到的区间（`app/eval/stats.py` 的 `bootstrap_ci`），提醒题量不大时不要把一个点看成精确成绩。闲聊、日历、拒答比较容易通过，所以门禁看的是核心完成率：事实、计算、多工具、以及「不该用工具」这四类（常量 `CORE_TASK_TYPES`）。

你怎么跑：这套默认目标是服务，本机虚拟环境连不上对象存储和向量库时，`preflight` 会直接拒绝，并提示用编排命令。见第 9 节。

## 4. 一道题怎么算做完，失败记在哪

判分函数在 `backend/app/eval/judges.py`，入口是 `judge_completion`。题型写在每道题的 `task_type` 上。

- `fact_qa`：答案满足结构化规格。该答却拒了，算失败。
- `compute`：沙箱应已执行。数字落在容差内，或满足规格。
- `refuse`：要有拒答说法，不能编造三位及以上的数字。这类题不参与忠实度和引用扣分。
- `chat`：不该引用知识库，路由不能明显走错。
- `calendar`：主要看是不是走了日历。
- `multi_tool`：规格里的每一项都要出现。
- `no_tool`：不该真的执行工具。要么答出规格，要么说明缺数据。

规格 `answer_spec` 常见几种：数字（带单位和容差）、时间区间、枚举（几种说法任一即可）、`all_of`（几项都要有）、纯文本包含。抽数字时用边界，避免短数字撞进长数字。中文数字如「十二」会先换成整数再比。

整段办事之外，其他套件用自己的失败列表，但和「基础设施故障」相关的约定是同一句：接口坏了不要算进「模型答错」。依据核验和上下文的真作答路径都会把 `infra_error` 单列。路由在模型抛 `RouterError` 时把预测记成 `error`，准确率下降，但不会冒充某种正确意图。

统一门禁不认识「第几层」。它只读报告里的数字。整段办事的门槛因此写成：核心完成率有下限，基础设施故障率有上限，完整档再加一条工具集合精确匹配的下限。这些数是 `gates.py` 里写死的地板，用来拦住明显退步，不是产品目标。过线只说明没有掉到地板以下。

## 5. 门禁和报告怎么落盘

`gates.py` 的 `GATES` 按「套件 + 档位」列出门槛。每条可以有绝对下限、绝对上限、相对上一份同档通过报告允许下跌多少（默认 0.05；故障率这类指标把下跌检查关掉）。指标从报告里消失，默认算失败，避免重构时把字段删了还显示通过。

现在写进去的门槛是：

- 路由两档：意图准确率、工具集合精确匹配，下限都是 0.87。
- 检索两档：召回下限 0.93，正确文档排位（`mrr`）下限 0.88。
- 整段办事冒烟：核心完成率下限 0.30，基础设施故障率上限 0.05。完整档核心完成率下限 0.45，工具精确匹配下限 0.55，故障率上限仍是 0.05。
- 依据核验冒烟只卡拒答准确率下限 0.40。完整档再加忠实度均值下限 0.70，拒答下限 0.60。
- 表格冒烟卡计划准确率下限 0.90。完整档卡执行准确率下限 0.80、连接成功题的比例下限是 10/14、规划失败率必须是 0。
- 上下文两档：不变量违规必须是 0，待办保留必须是 1，压缩率下限 0.05。

离线测试那一套没有写进 `GATES`。它的红绿就是 `pytest` 自己的退出码。

报告目录默认是 `backend/reports/`，可用环境变量 `EVAL_REPORTS_DIR` 换地方。一次运行留下：

```
reports/index.jsonl                          总索引，超过 2000 行会转成 index.jsonl.1
reports/<套件>/latest-<档位>.json             该档最近一次「可以当最新」的结果
reports/<套件>/latest-<档位>.md
reports/<套件>/latest.json                    最近一次通过的完整档；冒烟档不覆盖它
reports/<套件>/runs/<时间>_<档位>/report.json
reports/<套件>/runs/<时间>_<档位>/samples.jsonl
reports/<套件>/runs/<时间>_<档位>/summary.md
reports/<套件>/runs/<时间>_<档位>/stdout.log
```

`latest-档位` 的更新规则在 `write_run`：这次退出码是 0，或者这个档还没有任何最新文件，才覆盖。失败的运行仍留在 `runs/` 里，但不会变成别人眼中的「最新」，也不会变成下一次比较退步的尺子。`read_baseline` 往回找同档里最后一次退出码为 0 的 `report.json`。

`report.json` 的 `meta` 里有：套件、档位、目标、命令行、开始时间、耗时、`git_sha`、题集路径和哈希、相关输入文件的哈希、开跑前的设置快照、`run_stats`、退出码、目录。`git_sha` 优先读环境变量 `GIT_SHA`，否则在本机执行 `git rev-parse`。编排文件里把 `GIT_SHA` 透传进去了，但容器里没有 `.git`；你不在外面导出这个变量，容器里会记成 `unknown`。

输入哈希由 `hash_inputs` 和 `default_input_paths` 完成：总会带上 `data/eval/fixtures`；检索再带语料目录；整段办事和依据核验再带 `data/eval/seeds`。被忽略的本机考勤表不在这条哈希清单里。

整段办事的 `run_stats` 带有故障题数、延迟均值和分位、能测到的提示词词元总和。`eval.py` 还会并入 `llm_stats_snapshot`：凡是走过 `complete_text` 的调用，会累计次数、重试、基础设施故障、延迟和词元。不是每一套都有逐题延迟。

对比两次运行：`python scripts/eval.py diff <套件> --profile full`。它取该档目录里按名字排序的最后两份 `report.json`，用失败题编号做差，打印新挂的和新修好的。看最近一份：`python scripts/eval.py last <套件> --profile smoke`。不写档位时读的是 `latest.json`。

## 6. 题集从哪来，契约查什么

题集是生成器写出来的，不靠模型现场编题。

- `scripts/gen_office_eval.py` 写路由题。`gen_office_eval_500.py` 只是转调它的旧名字。
- `scripts/gen_rag_eval.py` 写检索题。`gen_rag_eval_500.py` 同样是旧名字。
- `scripts/gen_office_tabular_eval.py` 写表格题和夹具，金标准用清洗后的表重算。
- `scripts/gen_context_eval.py` 写上下文回放题。
- `scripts/gen_grounding_eval.py` 写依据核验题，证据来自审过的种子。
- `scripts/gen_agent_eval.py` 写整段办事题。
- `scripts/gen_yz_eval.py` 写已下线套件的历史题集，只供翻旧账。

考勤类数字若本机有 `backend/tests/YZ测试文档/测试用例.csv`，生成器会重算；这份文件被忽略，仓库和自动流水线默认没有。没有它时，`gen_agent_eval.py` 改读 `data/eval/seeds/yz_attendance.jsonl` 里冻住的数。

检查入口是 `python scripts/lint_eval_datasets.py`。它调用 `app/eval/contracts.py` 的 `validate_all` 和 `cross_dataset_checks`。

`validate_all` 按 `CONTRACTS` 逐套检查字段形状、行数范围、去重（`normalize_text` 去掉符号后再比）、以及每套自己的分布。`suite_contract_alignment_errors` 要求：注册表里每个带题集的套件都有契约，契约里也不许多出已下线的名字。`yz` 故意不在 `CONTRACTS` 里。

和整段办事相关的硬检查在 `_agent_check`：多轮占比、超短问法占比、同一题干变体不能超过两种、拒答题不能带标准文档或答案规格、事实和计算题必须有规格和标准文档、考勤汇总必须路由到沙箱、开关不能和标准工具矛盾。

跨题集检查看路由题和办事题：标了沙箱就必须声明「有表格」，标了知识库就必须声明「有文档」，办事题的意图必须和工具集合按同一规则推出来的意图一致。历史 `yz` 题若和这条约定冲突，`yz_label_conflicts` 只打印警告，不让检查失败。

「答案规格能不能从原文重算」没有放进 `contracts.py`。它落在测试 `tests/test_eval_datasets_contract.py`：汇总题对照冻结种子；多工具题在本机考勤表存在时对照重算结果，不存在就跳过。

`pytest.ini` 定义了三类标记：`unit`（不连外部）、`integration`（要本地应用）、`live`（会打到真模型或真服务）。目前只有评测基建的少数测试和数据库隔离测试打了这些标记，并没有覆盖全部测试文件。

聊天接口有一条不拆掉办事流程的测试：`tests/test_chat_sse_routing.py` 里的 `test_chat_sse_runs_real_workflow_with_fake_llm`。它用 `tests/conftest.py` 的 `fake_llm` 夹具把模型调用换成固定回复，然后真的打 `/api/chat`。同一文件里其他用例仍会替换 `_run_workflow_sync`。整份文件在缺少 `boto3` 时跳过。编排文件 `docker-compose.yml` 的 `eval` 服务已经把 `backend/tests` 挂进容器。

## 7. 走一遍：离线测试，再走一遍评测入口

下面两段都不需要启动数据库、对象存储、向量库或沙箱。工作目录是仓库里的 `backend`。

### 7.1 离线测试，和自动流水线同一条命令

```bash
cd backend
python scripts/lint_eval_datasets.py
python -m pytest tests -q
```

第一行进 `lint_eval_datasets.py` 的 `main`：对六套现役题集各跑一遍契约，再跑跨题集约定。某一套失败会打印具体行号和原因，进程退出码为 1。

第二行就是 `.github/workflows/eval.yml` 里 `offline` 任务的测试步骤（流水线还会先设临时库地址、关掉缓存、清空沙箱地址）。`pytest` 收集 `tests/` 下的用例。判分、门禁、报告、路由纯函数、表格清洗这些不需要外部服务。`test_rls_postgres.py` 发现当前不是那套隔离测试要的数据库时会跳过；那一项由流水线的 `rls` 任务单独跑。没有本机考勤表时，多工具题的重算会跳过。没有 `boto3` 时，聊天接口那份文件会跳过。

看某一小块也可以，例如只跑判分：

```bash
python -m pytest tests/test_eval_judges.py -q
```

这条只进 `judge_completion` 和数字边界，仍然不连模型。

### 7.2 评测入口，以上下文冒烟档为例

```bash
cd backend
python scripts/eval.py run context --profile smoke
```

入口 `main` 解析出套件名 `context`、档位 `smoke`，没有额外参数。然后 `_cmd_run`：

1. `get_suite("context")` 得到模块 `scripts.run_context_eval`，档位参数是 `--summarizer extractive --split smoke --arms legacy,full --gate`。默认目标是虚拟环境。这套 `requires` 为空，`preflight` 通过。
2. `make_run_dir` 建 `reports/context/runs/<时间>_smoke/`。
3. `bootstrap("venv", sqlite_path=这次目录/eval.db, isolate_app_db=True)` 把库指到这个文件，关掉缓存，清空沙箱地址，冻住「今天」。
4. `stub_blob_store_if_needed` 装一个假的对象存储，因为这套 `needs_blob_stub` 为真，而目标是虚拟环境。
5. 记下基线和设置快照，`llm_stats_reset` 把计数清零。
6. `_run_eval_suite` 导入 `run_context_eval`，`build_parser` 后把档位参数解析进去，调用 `run`。
7. `run` 确认没有同时打开「更新基线」和「门禁」，读出冒烟切片，对每题、每个臂调用 `replay_case`，再 `gate_report`。套件自己的门禁失败时，`SuiteResult.exit_code` 已是 1。
8. 回到 `eval.py`。这不是降级运行，于是 `evaluate_gates("context", "smoke", 报告, 基线)` 再查统一表里的三条：不变量、待办保留、压缩率。失败同样把退出码抬到 1。
9. `write_run` 落盘。终端最后两行是这次 `report.json` 的路径，和 `latest-smoke.json` 的路径。

想看刚才那份，而不必打开文件：

```bash
python scripts/eval.py last context --profile smoke
```

同一条入口换套件时，只有第 6 步换人。例如检索冒烟会进 `run_rag_retrieval_eval(..., production=False)`，走关键词对照；表格冒烟会进 `eval_plan`，只编译手写计划。这两条同样不用起服务：

```bash
python scripts/eval.py run rag --profile smoke
python scripts/eval.py run tabular --profile smoke
python scripts/eval.py run pytest --profile smoke
```

`eval.py run pytest --profile smoke` 和直接 `pytest tests -q` 不是同一范围：前者只跑注册表里那 10 个文件，后者跑整个 `tests/`。自动流水线用的是后者。

## 8. 对照改进方案：做完了、做了一部分、还没做

方案原文把七步标成五项已完成、三项未完成。下面按当前代码重判，不按方案文件头上的勾选。

**已完成**

- 失真缺陷。限流和超时在评测调用里会重试，最终抛 `LLMInfraError`（`complete_text_with_usage` 的 `raise_on_error=True`）。普通业务调用若没有打开这个开关，失败时仍可能得到空字符串，那是线上兜底，不是评测计分路径。表格否定词顺序、脏数字清洗、软通过计数、分档最新报告、缓存键含模型和提示词，都已落在第 3 节点名的函数里。`run_*.py` 仍在导入时调用 `ensure_bootstrap`，但入口先跑过之后它是空操作，并且各套件带上了是否隔离应用库的参数。
- 判分改造。`judges.py`、拒答、结构化规格、路由和检索的主指标、依据核验只打一次分、相关性不进门禁、「今天」冻结、联网证据带发布日期，都在。轨迹召回仍写入路由报告，只是退出了主指标和门禁。检索的标准答案仍是整篇文档，方案里可选的「块级标准答案」没有做。
- 单环节对齐生产路径。路由走 `plan_tools` 加上下文和日程短路；检索完整档走 `ingest_document` 加混合检索，退回关键词会失败；表格完整档走 `analyze_local_tables` 里的 `_plan_analysis_spec`；依据核验走 `ground_and_repair_answer`。
- 题集重建。六套现役题集都在，行数见第 2 节的表和第 3 节。拒答题不带标准文档，考勤汇总标成沙箱。历史 `yz` 题集还在，只供对照。
- 整段办事套件，以及从注册表移除 `yz`。实现是 `agent_e2e.py`，三层失败、联网桩、冻住的日期都在。题量是 174，不是方案草稿里的大约 200。

**做了一部分**

- 上下文的指标和真作答。规则摘要、不变量、待办、压缩率和摘要率拆开、压低长度上限、同一切片才许比基线、禁止「更新基线」和「门禁」一起开，这些已经在 `context_replay.py`。让模型作答的 `--live` 也能跑，但要手设 `RUN_CTX_EVAL=1`，不在注册表的冒烟档或完整档里，自动流水线也不跑它。因此现在的上下文分数回答的是「拼得对不对」，不是「答得对不对」。
- 统一门禁和报告设施。`GATES`、分档最新文件、`diff`、开跑前的设置快照、输入哈希、运行目录后缀、原子替换、索引轮转、整段办事的重抽样区间和逐题延迟，都有。缺口是：离线测试套件不在 `GATES` 里；重抽样区间只做了整段办事的完成率，没有铺到每一套会花钱的评测；逐题延迟和词元主要在整段办事，其他套件最多有一次运行的累计；容器里的 `GIT_SHA` 要你在外面导出，否则是 `unknown`；被忽略的本机考勤表本身不进输入哈希。方案里「同一提交跑两次，差别落在区间里」没有做成自动检查。
- 契约和离线测试补强。契约清单已经跟注册表对齐，跨题集标签、去重、多轮和超短问法、拒答不带标准文档，都有。行级隔离测试和「用普通账号跑」的流水线任务有了。`fake_llm`、一条真的办事流程的聊天测试、三类标记的定义、编排环境挂载 `tests/`，也都有。缺口是：答案规格的重算只在一条测试里、而且缺本机表会跳过；标记没有打到大部分测试上；聊天测试文件里多数用例仍替换掉办事流程，并且整文件依赖 `boto3`。

**还没做**

- 没有夜间定时去跑上下文的真作答档。代码开关不等于调度。
- 没有「每个会打模型的套件都带重抽样区间」。
- 没有在契约层对全部答案规格做语料或表格复算。

对外只讲整段办事的完成情况，并写上档位、题量、区间和基础设施故障有多少。冒烟档、关键词检索、手写表格计划、规则摘要，都不能当这条成绩。

## 9. 本机不想启动服务时，可以跑什么

都在 `backend` 目录。不需要数据库、对象存储、向量库、沙箱进程。

```bash
python scripts/eval.py list
python scripts/lint_eval_datasets.py
python -m pytest tests -q
python scripts/eval.py run pytest --profile smoke
python scripts/eval.py run rag --profile smoke
python scripts/eval.py run tabular --profile smoke
python scripts/eval.py run context --profile smoke
python scripts/eval.py last context --profile smoke
```

路由冒烟不连服务，但要一份对得上当前模型和提示词的缓存。没有就不要指望它变绿，按它打印的提示去跑完整档，而那一次需要模型密钥。

下面这些会在 `preflight` 或套件内部停下来，直到服务和密钥齐：

```bash
python scripts/eval.py run agent --profile smoke
python scripts/eval.py run grounding --profile smoke
python scripts/eval.py run rag --profile full
python scripts/eval.py run tabular --profile full
```

整段办事入库还要那三份夹具都在磁盘上。干净检出里只有制度正文和产品说明，考勤表不在仓库里。文件缺失时跑不起来，和「服务没起来」是两件不同的事。

服务和夹具都齐了以后，用编排环境跑：

```bash
export GIT_SHA=$(git rev-parse --short HEAD)
docker compose --profile eval run --rm eval \
  python scripts/eval.py run agent --profile smoke
```

`eval` 这个服务默认不随普通启动拉起。它依赖数据库、缓存、向量库、对象存储和沙箱都健康，并把应用代码、脚本、数据和 `tests/` 挂进去。应用库是否改绑临时文件，仍由套件的 `isolate_app_db` 决定：整段办事和依据核验用真库。

自动流水线里，每次推送和拉取请求跑 `offline` 与 `rls`。要模型或整套服务的套件不在每次推送里。手动触发工作流时，才会再跑一轮不花钱的冒烟：离线测试、检索、表格、上下文。
